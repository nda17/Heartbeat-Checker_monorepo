# Heartbeat-Checker_monorepo

## Архитектура:

Heartbeat Checker - коммерческий сервис проверки доступности сайтов, API, TCP-портов и серверов по ICMP. Пользователь управляет мониторингом через сайт и получает уведомления о падении и восстановлении.

Домен проекта — `heartbeat-checker.ru`, публичный origin — `https://heartbeat-checker.ru`. Домен не меняет локальные адреса и тестовые ключи. Production-сборка `app` подключает Go API; режим `frontend` открывает страницы сайта и формы авторизации без backend, поэтому `/api/v1/*` возвращает `503` с `temporarily_unavailable` и регистрация и вход в этом режиме недоступны. Режим `landing` оставляет только главную страницу и документы. Фактическое состояние развертывания и проверок фиксируется в корневом `../context.md`.

Документ разделяет реализацию, конфигурацию деплоя и целевые продуктовые требования. Служебные письма auth проходят через очередь; добавлены независимые боты поддержки Telegram/MAX и зашифрованные ежедневные backup в S3. Informer Telegram/MAX и email-уведомления мониторинга защищены отдельными флагами; email требует подтверждения адреса и включения для каждого монитора. Административный интерфейс включает MFA, аудит и выдачу квот. Интеграция API ЮKassa поддерживает тестовый магазин для владельца и отдельный production-магазин для всех активных аккаунтов. Возвраты и автопродление остаются следующими этапами. Точный опубликованный source и результаты внешней приёмки фиксируются в `../context.md`.

### Текущее состояние и запуск

Работают Go API авторизации, профиля, квоты и мониторов, отдельные `worker` и `probe`, Next.js лендинг и кабинет. API использует PostgreSQL, структурированные логи и корректное завершение. `/healthz` проверяет HTTP-сервер, `/readyz` выполняет Ping БД с таймаутом; при недоступной БД readiness возвращает 503, после восстановления — 200.

Требуются Go 1.27+, Node.js 24.21+, Docker с Compose и `make`. PostgreSQL 18.6 запускается на `127.0.0.1:55432`, Mailpit принимает локальную почту на `127.0.0.1:51025`, его UI доступен на `http://127.0.0.1:58025`. Данные БД сохраняются в volume локального Compose-проекта.

Из корня монорепозитория:

```sh
make local-up   # PostgreSQL и локальный SMTP-приемник Mailpit
make init-local # Создать игнорируемые секреты worker/probe и webhook
make migrate    # Применить SQL-миграции отдельной командой
```

В отдельных терминалах запустите процессы:

```sh
make run     # Go API на 127.0.0.1:8080
make probe   # Изолированный исполнитель проверок на 127.0.0.1:8090
make worker  # Планировщик проверок и очистка данных
```

Для сайта установите зависимости из lockfile и запустите Next.js на `http://127.0.0.1:3000`:

```sh
cd apps/web
cp .env.example .env.local
npm ci
cd ../..
make web-dev
```

В `.env.local` адрес `GO_API_ORIGIN=http://127.0.0.1:8080` нужен серверному proxy Next.js; браузер обращается к API через origin сайта `http://127.0.0.1:3000`. Для локального запуска production-сборки frontend используйте из `apps/web` команды `npm run build` и `npm start` с той же конфигурацией. Это локальный режим сборки, а не развертывание публичного сайта.

Проверки и служебные команды:

```sh
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
make check             # gofmt, go vet, Go-тесты и сборка backend
make test-integration  # HTTP/SQL-сценарии в отдельных временных БД
make test-smtp-auth    # PostgreSQL и Mailpit, заглушка капчи
make test-live-auth    # Реальные Siteverify и Mailpit; нужна внешняя сеть
```

`make db-up` запускает только PostgreSQL, `make mail-up` — только Mailpit. `make db-down` останавливает контейнеры локального Compose-проекта, сохраняя volume БД. Почта Mailpit временная и не сохраняется после удаления контейнера. Тестовые учетные данные предназначены только для локального окружения.

`make run` задает локальные значения `DATABASE_URL`, `AUTH_ORIGIN=http://127.0.0.1:3000`, cookie, Turnstile и SMTP; экспортированные переменные их переопределяют. API сохраняет служебные письма в зашифрованную очередь, а `make worker` доставляет их в Mailpit. Для проверки регистрации нужны оба процесса. `make init-local` создает с правами `0600` постоянные `.local/probe-secret`, `.local/webhook-key` и `.local/auth-mail-key`, не перезаписывая существующие значения. API и worker читают ключи webhook и auth mail; probe и frontend их не получают. При переносе БД сохраняйте `WEBHOOK_ENCRYPTION_KEY` и `AUTH_MAIL_ENCRYPTION_KEY`: первый нужен для адресов и секретов уведомлений, второй — для ожидающих писем и подтверждения кодов. При прямом запуске Go обязательны переменные соответствующего процесса из `.env.example`. API не применяет миграции автоматически. `make migrate` блокирует конкурентное применение, записывает контрольные суммы и отклоняет изменение уже примененного SQL.

`.env.example` описывает параметры и не загружается автоматически; приложения читают environment. Таймауты API по умолчанию: соединение с БД 5 секунд, readiness 2 секунды, завершение 10 секунд.

Новый аккаунт получает квоту 0: регистрация сама по себе не разрешает создать монитор. Только для локальной разработки выдайте квоту явно, взяв `account.id` из `GET /api/v1/me` после входа:

```sh
make grant ACCOUNT_ID=ваш-uuid LIMIT=2 UNTIL=2026-11-18T00:00:00Z
```

Команда работает только при `APP_ENV=local` и подключении к проектной loopback-БД; источник `local_test` в production не считается действительным правом. Монитор создается и включается только в пределах действующей квоты. Доступ к тестовой оплате регулируется отдельно и не предоставляется автоматически при регистрации.

Для первоначального локального администратора есть отдельная create-only команда. Она в одной транзакции создает активный профиль с ролью `admin`, учетные данные и тестовую квоту. Существующий email, в том числе при конкурентном запуске, приводит к отказу без изменения профиля, пароля, сессий и квоты. Обычная регистрация всегда создает роль `user`.

Создайте файл `.local/admin-password` локально через редактор или скрытый ввод, без пароля в командах, аргументах или environment. Файл должен быть обычным, с правами `0600`, и содержать ровно пароль длиной 12–1024 байта. Пробелы и переводы строк сохраняются как часть пароля: не добавляйте завершающий перевод строки. Symlink и другие типы файлов отклоняются. `.local/` исключен из Git.

```sh
chmod 600 .local/admin-password
ADMIN_EMAIL=owner@example.test \
ADMIN_NAME='Local owner' \
ADMIN_QUOTA=10 \
ADMIN_UNTIL=2027-10-18T00:00:00Z \
ADMIN_PASSWORD_FILE=../.local/admin-password \
ADMIN_REASON='Explicit local owner bootstrap' \
make local-admin
```

`ADMIN_PASSWORD_FILE` в этой Make-команде задается относительно `backend/`; остальные параметры также обязательны и выбираются явно. Для прямого запуска: `cd backend`, затем `APP_ENV=local bin/local-admin --email … --name … --quota … --until … --password-file … --reason …`. Команда сначала проверяет `APP_ENV=local` и точный адрес проектной loopback-БД, а уже затем читает пароль и подключается к PostgreSQL. Hash Argon2id вычисляется до транзакции. Команда не отправляет письмо, не создает сессию и не выдает оплаченный доступ; тестовая квота имеет источник `local_test` и выбранный срок.

Администратор входит через обычную форму с Turnstile и использует собственный кабинет мониторинга. Для `/app/admin` и `/api/v1/admin/*` дополнительно нужна активная TOTP MFA: после входа начальная сессия не имеет административных прав, пока не подтвержден фактор. Чтение требует подтверждения не старше 12 часов, изменение — свежего шага с текущим паролем и кодом не старше 5 минут. Привязка и замена фактора подтверждаются кодом; 10 одноразовых кодов восстановления показываются только при выдаче, в БД лежат их SHA256. Подтверждение и восстановление меняют токен сессии и CSRF, отзыв ролей и блокировка отзывают все сессии, а сброс пароля не удаляет MFA. Фактор шифруется отдельным `AUTH_MFA_ENCRYPTION_KEY`, необходимым только API. Локальный CLI собирается в `make check` и CI, но не включается в production-образы. После успешного запуска удалите файл с паролем, когда он больше не нужен.

Административный API позволяет искать аккаунты, менять имя, роль и статус, отзывать сессии, выдавать или отзывать квоту и управлять мониторами владельца. Изменения требуют причины и актуальной версии записи; действие и запись в `admin.audit_events` фиксируются в одной транзакции. Нельзя заблокировать или лишить роли себя либо последнего активного администратора. Административная часть квоты хранится отдельно от подписки, действует в production до собственного срока и складывается с действующей оплаченной частью. Выдача, изменение и отзыв административной части не меняют оплаченный период; версия запроса охватывает оба компонента. Уменьшение общей квоты не удаляет мониторы: включённые сверх лимита переходят в `SUBSCRIPTION_REQUIRED`. Перенос owner в production — отдельная create-only операция CI с audit-маркером; наличие кода не означает, что перенос, MFA-привязка и живая приёмка уже выполнены.

Пользователь может без восстановления удалить свой аккаунт через `DELETE /api/v1/me` с текущим паролем и `expectedAccountId`; запрос требует действующие сессию, Origin и CSRF и ограничен 20 попытками на IP и 5 на аккаунт за 15 минут. Изменение атомарно переводит профиль в `deleted`, отзывает сессии и токены, освобождает прежние email и OAuth-привязки для новой регистрации с новым UUID, стирает рабочие данные мониторинга и уведомлений и отменяет ожидающую отправку. UUID и минимальные технические записи об оплате сохраняются без имени, адреса и пароля. Администратор сначала должен передать роль другому администратору, а аккаунт без пароля — установить пароль через существующий сценарий восстановления. Уже начатая внешняя отправка может завершиться; повтор после удаления не планируется. Псевдонимные SHA256-маркеры кратких окон защиты от злоупотреблений сохраняются до штатной очистки, а HMAC-маркеры общей очереди ограничений отправки без открытого адресата — до суточной очистки. Независимые обращения к Support-ботам не связаны с `account_id` и этой операцией не удаляются.

Для auth/accounts прошли `make check`, `go mod verify`, тесты с `-race` и реальной PostgreSQL, повторное применение миграций, SMTP smoke и `make test-live-auth`. Живой сценарий проверил Siteverify с официальными тестовыми ключами, регистрацию, письмо, подтверждение, вход, сброс пароля, отзыв старой сессии и повторный вход; временные БД и письма тестов удалены. Сквозная HTTP-проверка через Next.js proxy подтвердила регистрацию, подтверждение, вход, отказ без квоты (`403`), отказ при исчерпании квоты (`403`) и CSRF (`403`). Отдельные worker/probe получили реальный UP/HTTP 200 от example.com; два несовпадения ожидаемого кода открыли один инцидент. После перехода на места для включённых мониторов пауза освобождает место без удаления сохранённого монитора.

В Chrome проверены кабинет авторизованного тестового аккаунта, история результатов/инцидентов, редактирование условия и завершение инцидента с причиной «Настройки изменены», отображение профиля и двух сессий. Полная браузерная проверка регистрации, изменения профиля, отзыва сессий и мобильной верстки пока не завершена: управление периодически блокируется UI другого расширения. Эти сценарии нельзя считать принятыми только по API-тестам.

GitHub CI проверяет Go и frontend, интеграционные сценарии, конфигурацию обоих деплоев и откат, затем собирает образы API, worker, probe, migrate и web в режимах `app`, `frontend` и `landing`. Workflow `Deploy backend` развертывает Go-стек на отдельном VPS; `Deploy frontend` доставляет web на frontend VPS. Режим `frontend` открывает главную, документы, формы авторизации и страницы кабинета без backend; API возвращает `503` без сессий и кэширования, а операции с аккаунтами и мониторами недоступны. Режим `landing` публикует только главную и документы; полноценный режим `app` требует успешного backend-деплоя и реального `GO_API_ORIGIN`. На сайте указан контакт `info@heartbeat-checker.ru`; прием почты по этому адресу проверяется отдельно от исходящей служебной почты.

При подключении и замене MFA кабинет показывает QR-код, сформированный локально из `otpauthUri`, ссылку для приложения и ключ ручного ввода. Секрет не отправляется сервисам генерации QR и не записывается в хранилища браузера. После подтверждения обновляются сроки доступа и административные данные без перезагрузки; ответы запросов старой сессии игнорируются. Успешное сохранение отделено от последующей загрузки: при сбое обновления можно повторить чтение, не выполняя изменение заново. Регрессии интерфейса запускаются командой `npm run test:ui` в `apps/web` и включены в CI.

В режиме `app` переход с главной ведёт в `/app`; формы входа и регистрации сначала проверяют сессию. Вошедший пользователь сразу попадает в кабинет, а ошибка или таймаут проверки дают ручной повтор. Шапка главной обновляет состояние входа при возвращении на страницу. Предложения установить приложение скрываются при `display-mode: standalone` или точном Android-referrer нашего APK; этот сигнал влияет только на интерфейс, не на авторизацию. CCT fallback без этих признаков требует отдельной проверки на устройстве.

На узком экране навигация кабинета раскрывается кнопкой «Меню», таблицы мониторов, результатов, инцидентов и заказов показываются карточками с подписями полей. Начальная загрузка сессий, оплаты, способов входа и чатов имеет ограниченное ожидание и ручной повтор; ошибки сохранения находятся рядом с соответствующим действием. В Chrome проверены ширины 320/360/390/430 px с локальными демонстрационными данными, длинные названия, история и ошибка URL. Это проверка веб-интерфейса; работа системной клавиатуры, Android Back, настоящего OAuth и React Native-приложения на телефоне остаётся отдельной приёмкой.

Мониторы поддерживают HTTP/HTTPS, TCP и ICMP с публичными целями. Для HTTP/HTTPS успех определяется ответом HTTP и заданными условиями; TCP проверяет соединение с портом, ICMP — получение Echo Reply. Для HTTPS проверяется сертификат; автоматического перехода на HTTP нет. Результаты различают таймаут, недействительный TLS-сертификат, ошибку TLS-соединения и прочие ошибки запроса. Исторический `request_failed` сохраняется и отображается общим пояснением.

### Часовой пояс и провайдер монитора

`timeZone` задаётся отдельно для монитора, по умолчанию `Europe/Moscow`, включая существующие записи. `GET /api/v1/monitor-time-zones` возвращает общий каталог IANA с русскими названиями из Unicode CLDR48; форма ищет по городу и IANA ID. В кабинете и отчётах email/Telegram/MAX/push первое нарушение, подтверждение и восстановление показываются в выбранном поясе со смещением на дату события, включая летнее время. Длительность считается между исходными моментами времени. Изменение названия или пояса сохраняет активную проверку и инцидент; версии публичного редактирования и конфигурации проверок разделены. Уже созданные задания уведомлений сохраняют свой снимок; исторический снимок без пояса отображается по Москве. Если браузер не знает выбранный пояс, кабинет явно показывает UTC вместо него.

«Провайдер / CDN» определяется асинхронно при создании монитора и изменении нормализованного домена/IP. Имя сети берётся из локального снимка [IPtoASN](https://iptoasn.com/) (PDDL1.0); внешний lookup для каждого probe не выполняется. Worker отдельно обновляет проверенный снимок в volume `provider-asn-cache`, путь задаёт `PROVIDER_ASN_CACHE_DIR` (по умолчанию `/var/lib/heartbeat/asn`). При отсутствии источника проверки мониторов продолжаются, обогащение ждёт доступного снимка. Для нескольких публичных адресов показываются до трёх названий; при отсутствии данных — «Неизвестно». Это сведения о сети или CDN, а не физическом дата-центре. Самостоятельная смена DNS без редактирования цели не запускает повторное определение; время определения видно в карточке. Обогащение не сбрасывает историю или активную проверку, а старый lookup не перезаписывает изменённую цель.

### Подготовка frontend VPS и доставка

Frontend размещается отдельно от Go и PostgreSQL. Скрипт `deploy/frontend/bootstrap.sh` предназначен для чистой Ubuntu 22.04/24.04/26.04 amd64: устанавливает Docker Engine и Compose из официального подписанного репозитория, создает пользователя `heartbeat-deploy` и каталог `/opt/heartbeat-checker/frontend`. Один публичный SSH-ключ передается через stdin:

```sh
sudo bash bootstrap.sh < /path/to/frontend-deploy-key.pub
```

До подключения сверяется SSH host key сервера. Bootstrap сохраняет существующий root/парольный доступ и настройки firewall; ключ CI запрещает PTY и forwarding. Пользователь входит в группу Docker и поэтому имеет административные возможности на этом выделенном VPS. Приватный ключ не включается в исходники.

В GitHub Actions нужны следующие repository variables и secrets:

| Тип | Имя | Назначение |
| --- | --- | --- |
| Variable | `WEB_PUBLIC_ORIGIN` | `https://heartbeat-checker.ru` |
| Variable | `GO_API_ORIGIN` | Только для режима `app`: реальный HTTPS origin отдельного Go API; в `frontend` и `landing` не передается |
| Variable | `TURNSTILE_SITE_KEY` | Для режимов `app` и `frontend`: настоящий публичный site key для домена |
| Variable | `FRONTEND_DEPLOY_HOST` | IP или имя frontend VPS |
| Variable | `FRONTEND_DEPLOY_USER` | `heartbeat-deploy` |
| Secret | `FRONTEND_DEPLOY_SSH_KEY` | Отдельный приватный ключ CI |
| Secret | `FRONTEND_DEPLOY_KNOWN_HOSTS` | Проверенные SSH host keys сервера |

Секрет Turnstile нужен только Go и не передается frontend или его сборке. В режиме `landing` upstream API и публичный site key передаются в сборку пустыми независимо от repository variables. В режиме `frontend` API origin пустой, но требуется настоящий публичный site key Turnstile; в режиме `app` нужны и настоящий API origin, и site key. Не задавайте временный чужой IP или origin сайта вместо backend.

`Deploy frontend` запускается вручную из `master` с полным `source_sha` и выбором `web_mode`: по умолчанию `app`, либо `frontend` или `landing` без backend. Он проверяет присутствие коммита в истории master и успешный push-CI именно этого SHA, собирает web с production-параметрами, публикует отдельный тег `SHA-mode` в GHCR и передает immutable digest на VPS. Краткоживущий registry token передается через stdin; временные Docker credentials удаляются. Образ проверяется по OCI revision и метке режима до переключения. Параллельные релизы сериализованы.

Compose запускает web в закрытой сети без host-порта 3000 и Caddy с автоматическим HTTPS. Для Caddy нужны доступные 80/443 TCP и 443 UDP; сертификаты сохраняются в Docker volume. API/auth не кэшируются. В режиме `app` frontend Caddy перезаписывает `X-Heartbeat-Client-IP` адресом непосредственного клиента, а Next.js передает его через same-origin `/api/v1/*` proxy. До переключения frontend проверяет ответ Go `/api/v1/me` — `401` с `unauthorized`, после запуска — тот же ответ через публичный origin. В режиме `frontend` preflight API отсутствует; postflight проверяет главную со ссылками на вход и регистрацию, ответы `200` страниц документов, авторизации и кабинета, `/theme-init.js`, а также `503` и `temporarily_unavailable` без `Set-Cookie` и с `Cache-Control: no-store` для GET `/api/v1/me` и POST `/api/v1/auth/login`. В режиме `landing` postflight проверяет главную со ссылками на документы, ответы `200` этих страниц, `/theme-init.js`, `404` на `/api/v1/me` и перенаправление auth-страниц и кабинета на главную. Неуспех восстанавливает предыдущие image/config; при неудаче первого запуска контейнеры останавливаются без удаления volumes. При ошибке самого отката файлы остаются для восстановления. Предыдущая успешная конфигурация сохраняется в `previous/`.

Bootstrap и конфигурация проверяются в CI, сценарии переключения/отката покрыты изолированными тестами. Публикация `landing` не означает готовность коммерческого сервиса: backend, реальная служебная почта, платежи и уведомления требуют отдельных проверок и включения.

### Уведомления Informer о мониторинге

`MESSENGER_NOTIFICATIONS_ENABLED=false` оставляет новую доставку выключенной. При включении кабинет создаёт одноразовую привязку на 10 минут: пользователь запускает Informer-бота Telegram или MAX по ссылке, API сохраняет только хеш токена, worker проверяет кандидата, а владелец аккаунта подтверждает показанные ему чат и пользователя. Для Telegram-группы или форумной темы сначала нужна привязанная личная учётная запись администратора; команда `/connect@бот <токен>` и проверки `getMe`, `getChat`, `getChatMember` не позволяют незаметно выбрать общий чат вместо темы. MAX поддерживает только личную доставку по `user_id` из события `bot_started`; `chat_id` не принимается за ID пользователя. Отдельные webhook `/webhooks/notifications/telegram` и `/webhooks/notifications/max` требуют свои секреты, ограничивают тело 1 MiB и не получают токены ботов в API.

Привязка различает реальное истечение срока (`expired`, `errorCode: link_expired`) и отказ проверки до срока (`failed` с ограниченным `errorCode`). Для обычной группы и топика Informer и отправитель должны быть администраторами; команда отправляется от того же личного Telegram-профиля, без анонимной отправки и отправки от имени группы. Создание групповой привязки без готовой личной возвращает `409 telegram_private_required`. Исторические `expired` без причины остаются неопределёнными: интерфейс не приписывает им истечение срока. Статус задаёт сервер; клиентские часы его не меняют. «Начать заново» создаёт новую ссылку по явному нажатию, без повторного использования или продления старого токена.

Для каждого монитора и провайдера выбирается подтверждённый адресат, включение и интервал напоминаний: 0, 15, 30, 60, 180, 360 или 1440 минут. При подтверждении сбоя и восстановлении исходный результат проверки, её тип, имя, адрес и номер инцидента шифруются в задании вместе с неизменным временем события. Напоминание создаётся только на очередной принятой проверке DOWN после наступления срока; пропущенные интервалы не догоняются. Сообщения используют выбранный часовой пояс монитора и сведения «Провайдер / CDN», код HTTP при его наличии, длительность проверки соответствующего типа и ICMP RTT только при успешном ответе. Ссылка на инцидент доступна для всех типов, «Открыть сайт» — только для HTTP/HTTPS. Отключение маршрута, смена адресата, пауза или удаление монитора отменяют старые задания. Перед отправкой worker снова проверяет активность аккаунта, монитора, подписки, адресата и актуальность инцидента; права Telegram-группы или темы перепроверяются перед каждым сообщением. Одновременно допускаются не более четырёх внешних попыток; новые попытки каждого провайдера запускаются не чаще раза в секунду для Telegram и раза в 0,5 секунды для MAX, интервалы продлеваются после завершения. Отдельная пауза действует для каждого получателя. Попытки ограничены восемью за 24 часа, а задания одного маршрута идут по порядку. После успешного ответа провайдера, но до записи результата в БД, повтор может создать дубль сообщения: внешние API не гарантируют exactly-once.

Используется существующий `WEBHOOK_ENCRYPTION_KEY` с отдельным доменом шифрования для Informer. API требует только секреты webhook и публичные адреса ботов; worker получает токены `TELEGRAM_BOT_INFORMER_TOKEN` и `MAX_BOT_INFORMER_TOKEN`. Отсутствие старого ключа после восстановления БД делает привязки и ожидающие доставки недоступными. Реальная регистрация webhook, включение флага и приёмка доставки выполняются отдельно после деплоя; наличие очереди само по себе не доказывает доставку пользователю.

### Android push через RuStore, FCM и Huawei

`ANDROID_PUSH_ENABLED=false` оставляет push выключенным. При включении API и worker получают публичный `RUSTORE_PUSH_PROJECT_ID`; секрет `RUSTORE_PUSH_SERVICE_TOKEN` получает только worker. Токены устройств и снимки уведомлений шифруются существующим `WEBHOOK_ENCRYPTION_KEY` с отдельными доменами. Сервисный токен не передаётся в APK, API, frontend, probe и логи. Активация выполняется отдельным запуском `Deploy backend` с `activate_android_push=true`, остальными activation-флагами `false` и проверенной конфигурацией RuStore и FCM; существующие значения проектов и ключей не ротируются.

FCM включается через `FCM_PUSH_ENABLED`; нужны публичный `FCM_PROJECT_ID` и worker-only `FCM_SERVICE_ACCOUNT_BASE64`. Закрытый ключ не передаётся API или APK. Поддержка Huawei подготовлена в исходниках 0.30 / Android 2.2.0 (`versionCode 11`); наличие кода не означает активацию серверного провайдера, публикацию APK или приёмку доставки.

Для Huawei сначала в AppGallery Connect проверяются существующий package `ru.heartbeatchecker.app`, постоянный release-сертификат SHA256 и включённый Push Kit. В ignored `.local/push-cloud` сохраняется исходная клиентская конфигурация; в Git и APK не попадают серверный OAuth secret или исходный JSON целиком. Публичные repository variables `HUAWEI_APP_ID`, `HUAWEI_PROJECT_ID`, `HUAWEI_CP_ID` берутся из конфигурации одного приложения. Это разные идентификаторы: `PROJECT_ID` означает проект AppGallery Connect, а `APP_ID` — приложение. В защищённом environment `production-backend` нужны secrets `HUAWEI_CLIENT_ID` и `HUAWEI_CLIENT_SECRET` для OAuth именно этого приложения. `CLIENT_ID` проверяется по порталу отдельно и не подменяется идентификатором проекта; Android send API использует `/v1/{clientId}/messages:send`. Приватные credentials получает только worker. Перед активацией владелец сверяет соответствие app/project/OAuth client/package/сертификата в портале.

Huawei подключается явно: кандидат `Build or publish Android` собирается с `enable_huawei=true`; без этого флага Huawei отключён и публичные Huawei-поля пустые. Включённая сборка требует все три публичных идентификатора. Workflow сверяет их со значениями внутри manifest готового APK и сохраняет `huawei-config.json`, связанный с SHA256 этого APK. При отдельной публикации нужно повторить тот же `enable_huawei`; проверяются сохранённая конфигурация и неизменяемый APK. `dev`, `sdkTest` и обычный CI работают с отключённым Huawei; отдельные dev package/подпись не получают production push-конфигурацию. Серверная активация выполняется `Deploy backend` с `activate_android_push=true` и `activate_huawei_push=true`, остальные activation-флаги выключены. Существующие RuStore/FCM значения сохраняются, их отключение или ротация через эту операцию запрещены. Неполная конфигурация блокирует активацию без вывода credentials.

После входа из APK и выдачи разрешения телефон автоматически связывается с точной web-сессией. Ручное сравнение кодов и отдельный выбор телефона для каждого монитора не требуются. Первая успешная привязка с разрешением включает Push по умолчанию для существующих и будущих мониторов. Один переключатель Push у монитора действует на все текущие и будущие подключённые телефоны; явно сохранённое выключение сохраняется при повторном входе, подключении другого телефона и повторной выдаче разрешения. `GET/PUT /api/v1/monitors/{id}/push` возвращают `{enabled,version}`; PUT принимает те же поля и сохраняет явный выбор даже до подключения первого телефона. Версия `0` означает наследование значения аккаунта.

Привязка использует PKCE S256, локальный случайный `clientState` и одноразовый `completionCode`. Bootstrap передаёт только challenge, state и метаданные устройства. Авторизованный POST подтверждения с Origin/CSRF возвращает код только браузеру; в БД хранится SHA-256 кода. Метаданные и native polling код не возвращают. APK обменивает полученный через точный callback код вместе с verifier, токеном выбранного push-провайдера и разрешением; подтверждённая сессия повторно проверяется в той же транзакции. Потерянный ответ подтверждения требует новой попытки привязки; после неоднозначного обмена приложение сверяет `lastPairingId`, а не повторяет обмен вслепую. Начало новой попытки не отключает действующую привязку. Повторный успешный вход в тот же аккаунт с той же сессией сохраняет поколение привязки; новая сессия или аккаунт отменяют прежние доставки.

Привязка действует до истечения или отзыва исходной сессии; выход, смена аккаунта и отключение телефона прекращают получение текста. Выбранный push-провайдер получает только непрозрачные идентификаторы доставки: приложение авторизованно запрашивает текст после повторной проверки сессии, подписки, монитора и действующего переключателя Push. DOWN и UP идут по порядку отдельно для каждого монитора и телефона; повтор после потерянного ответа провайдера использует тот же ID доставки. Выключение Push отменяет ожидающие доставки и меняет поколение настройки. Готовность очереди и зелёные тесты не заменяют проверку доставки на реальном телефоне. APK автоматически выбирает доступный разрешённый сервером транспорт в порядке FCM → Huawei HMS → RuStore, включая ранее привязанные установки. Сначала он получает валидный токен более приоритетного транспорта и лишь затем атомарно заменяет локальные provider/token; при ошибке получения токена прежний маршрут сохраняется. Временные ошибки сервисов текущего транспорта не переключают установку на менее приоритетный. Опоздавший результат после тайм-аута, выхода, смены сессии или привязки не меняет маршрут. Следующая штатная регистрация обновляет существующую серверную установку с проверкой registrationVersion. Ручного выбора транспорта у пользователя нет. При первом получении задания worker фиксирует provider/token/version. Уже начатые доставки сохраняют этот маршрут при повторах, включая смену транспорта или токена; задания, которые worker ещё не получал, используют актуальный маршрут при первом получении. Старые APK без поля provider сохраняют маршрут RuStore. Наличие SDK, конфигурации и зелёного CI не является приёмкой FCM/RuStore/Huawei: отдельно нужны подписанный APK и реальные устройства с соответствующими сервисами, проверка foreground/background, DOWN/UP, отказов и отключения. Отправка в RuStore на модерацию остаётся отдельным решением владельца после ручных тестов.

После выхода или смены аккаунта внутри уже открытого кабинета прежняя сессия больше не разрешает доставку. Новая автоматическая привязка выполняется при следующем запуске APK; в настройках также доступен явный переход к настройке текущего телефона. Обычный Android-браузер сам приложение не запускает.

### Поддержка Telegram и MAX

Модуль `support` входит в тот же Go-монолит. Публичный API принимает только `POST /webhooks/support/telegram` и `POST /webhooks/support/max`; каждый endpoint проверяет собственный секрет заголовка и ограничивает тело 1 MiB. Caddy удаляет секретные заголовки из access/error logs. API не получает токены ботов. Worker обрабатывает зашифрованный PostgreSQL inbox и отправляет сообщения отдельными Support-ботами.

Telegram-клиент пишет боту, обращение копируется в заданную группу и support-топик. Только reply администратора в этом топике возвращается исходному клиенту. MAX-клиент пишет своему Support-боту, обращение попадает в отдельную закрытую MAX-группу; ответ администратора через reply возвращается в MAX. Обычные сообщения операторов не отправляются клиентам. Проверки прав выполняются перед доставкой; маршруты хранятся по провайдеру, операторскому чату и ID сообщения. Межплатформенной пересылки нет. Informer-боты используются отдельно для отчётов и подготовленных уведомлений о мониторинге.

При первом запуске Telegram `/start` или [MAX `bot_started`](https://dev.max.ru/docs/chatbots/bots-coding/prepare) Support-бот отправляет одно приветствие в личный чат. После успешной передачи обращения оператору он отправляет клиенту отдельное подтверждение; операторский reply и неподдержанные обращения его не создают. Оба сообщения проходят через зашифрованную очередь с ограниченными повторами. Приветствие учитывается один раз на пользователя и провайдера, повторный `/start` его не возобновляет; после исчерпания попыток или 24 часов оно остается завершенным с ошибкой для диагностики. Для уже полученных до релиза запусков приветствие задним числом не создается.

Параметры перечислены в `.env.example`. `SUPPORT_ENABLED=true` требует отдельный 32-байтовый base64 `SUPPORT_ENCRYPTION_KEY`, секреты обоих webhook, токены Support-ботов и явные ID операторских групп/топика. При `MAX_SUPPORT_CHAT_ID=0` MAX-доставка выключена, диагностические события не назначают группу автоматически. Дополнительный CA-файл MAX подключается только к его HTTP-транспорту; проверки TLS не отключаются. Перед включением нужно проверить членство ботов и права чтения/отправки, затем зарегистрировать webhook у каждого провайдера на опубликованный endpoint и проверить настройки чтением API.

Очередь ограничена по объему и отправителю, адресаты имеют отдельные ограничения частоты; повторы ограничены и учитывают ошибки провайдера. После окончательной обработки содержимое inbox стирается, служебные записи обращений и подтверждений хранятся 30 дней, связи сообщений — 90 дней, минимальные discovery-события — 7 дней. HMAC-маркер приветствия без открытого ID пользователя сохраняется для запрета повторной отправки. Копии переписки в самом мессенджере требуют отдельного управления хранением. Потеря ответа провайдера после отправки до фиксации результата может привести к повторному приветствию или подтверждению: exactly-once доставки внешние API не гарантируют.

### Telegram proxy и его публикация

Heartbeat использует отдельный HTTPS proxy `messengers-proxy.heartbeat-checker.ru` на `185.184.122.62`. В каноническом backend `.env` заданы `TELEGRAM_API_BASE_URL=https://messengers-proxy.heartbeat-checker.ru/telegram-api` и `TELEGRAM_API_PROXY_IP=185.184.122.62`; те же настройки передаются support, отчетам платежей и backup. IP меняет только TCP-назначение, сертификат проверяется для hostname URL. Без настройки используется официальный `https://api.telegram.org`; произвольные URL, HTTP, перенаправления и environment proxy не допускаются.

Входящие адреса Telegram-ботов — `https://messengers-proxy.heartbeat-checker.ru/webhooks/support/telegram` и `https://messengers-proxy.heartbeat-checker.ru/webhooks/notifications/telegram`. Relay передаёт только эти точные POST-маршруты в Go API и сохраняет секретные заголовки. Для исходящих запросов разрешены только `getMe`, `getChat`, `getChatMember`, `sendMessage`, `copyMessage`, POST и адрес backend VPS; URL с bot token и содержимое обращений не логируются. Регистрация webhook выполняется отдельно через официальный Telegram API, без удаления ожидающих обновлений.

Workflow `Deploy Telegram relay` запускается из `master` с полным `source_sha`, успешным push-CI того же SHA и `backup_sha256` локального архива проверенных nginx-конфигураций. Нужны secrets `RELAY_DEPLOY_SSH_KEY`, `RELAY_DEPLOY_KNOWN_HOSTS` и variable `RELAY_CERT_EMAIL`; отдельный SSH-ключ root для CI/CD явно разрешен владельцем, туннели и терминал запрещены. Архив конфигурации хранится у владельца вне Git/CI; приватные TLS-ключи и production-логи в него не экспортируются.

Деплой выпускает сертификат через certbot webroot, сверяет неизменность конфигурации и сертификата aeroCRM, проверяет оба направления proxy. По отдельному поручению владельца он удаляет известные nginx-конфигурации WinWidget, TCP listener и firewall-разрешение 8443, отдельные логи и lineage сертификата WinWidget. Общие nginx, certbot, SSH и системные службы сохраняются. До удаления сертификата ошибки откатывают nginx-конфигурацию; после начала необратимой очистки статус `cleanup_pending` требует проверки без восстановления удаленного сертификата. Текущий receipt хранится на relay в `/opt/heartbeat-checker/relay/receipt.txt`.

### Email-уведомления мониторов

Письма о подтверждённом сбое, восстановлении и продолжающемся инциденте используют фирменный HTML-шаблон с названием монитора, статусом, таблицей результатов и ссылкой на инцидент. Тема также содержит название монитора. Сохраняется текстовая версия письма; данные экранируются, время отображается в МСК (UTC+03). Шаблоны писем регистрации и подтверждения кодом не меняются.

`EMAIL_NOTIFICATIONS_ENABLED=false` по умолчанию. Канал использует SMTP worker независимо от Telegram/MAX; дополнительные токены ботов ему не нужны. Один аккаунт подключает один адрес уведомлений. Подтверждённый email для входа подключается сразу; другой адрес требует шестизначного кода из письма. Адрес для входа при этом не меняется. Подключение не включает доставку автоматически: канал и напоминания выбираются отдельно для каждого монитора.

`POST /api/v1/messenger-destinations/email` принимает `{email,destinationId,version}`: `200 {destination}` для уже подтверждённого адреса аккаунта либо `202 {challenge}` для подтверждения кодом. При первом подключении `destinationId=null, version=0`; замена требует текущих ID и версии. `GET /api/v1/messenger-destinations/email/verification` восстанавливает текущую попытку, `POST /verification/{id}/resend` повторяет письмо, `POST /verification/{id}/confirm` принимает `{code}` (оба пути под `/api/v1/messenger-destinations/email`). Код действует 10 минут, повторная отправка доступна не раньше чем через 60 секунд, допустимо пять неверных попыток. Общие ограничения отправки дополнительно защищают адрес от спама.

Пока новый адрес не подтверждён, прежний канал работает. После фактической смены адреса маршруты выключаются, ожидающие доставки отменяются; включить уведомления для нужных мониторов нужно заново. Повторное подключение того же адреса сохраняет настройки. Старый `POST {}` совместим с созданием/повторным подключением email аккаунта, но не может затереть другой адрес без проверки версии. Миграция `0020` сохраняет прежние адреса с их существующей проверкой владения; новый адрес получает отдельное подтверждение, которое учитывается при настройке, постановке в очередь и непосредственно перед отправкой.

Миграция `0017` добавляет `email_verified_at` без массового подтверждения старых или вручную созданных аккаунтов. Их вход, мониторинг и квоты продолжают работать. `POST /api/v1/me/email-verification` запрашивает письмо на текущий адрес; ссылка `/app/settings#verify-email=…` захватывается и очищается только после входа. Явная кнопка отправляет `POST /api/v1/me/email-verification/confirm`. Подтверждение не меняет пароль, версию учётных данных или сессии и не включает уведомления. Ссылка одноразовая и действует 30 минут; повторный запрос отзывает прежние незавершённые ссылки. Обычная и OAuth-регистрация, а также подтверждённое восстановление пароля записывают владение email после настоящей почтовой проверки.

Письма о сбое, восстановлении и напоминания проходят существующую зашифрованную очередь notifications: до восьми попыток за 24 часа, порядок внутри маршрута, повторная проверка аккаунта, квоты, адреса и настроек перед отправкой. Message-ID стабилен для одной доставки; постоянный SMTP-отказ завершает её без повторов. Успех означает принятие SMTP-сервером, но не попадание во входящие или прочтение. Отключение адреса/маршрута и удаление аккаунта останавливают следующие попытки; уже отправленный SMTP-запрос отозвать нельзя.

Активация — отдельный флаг `activate_email_notifications=true` workflow `Deploy backend`. Под общей блокировкой создаётся временный кандидат с единственным изменением `EMAIL_NOTIFICATIONS_ENABLED=true`; SMTP-параметры, ключи и остальные строки конфигурации сохраняются. Совмещать активацию с другими флагами нельзя. Реальную доставку на принадлежащий владельцу подтверждённый адрес нужно проверить отдельно после технического выпуска.

### Оплата через ЮKassa

`BILLING_PROVIDER=yookassa` и явный `YOOKASSA_MODE=test|production` выбирают магазин для веб-заказов и redirect checkout. Тестовый режим требует `YOOKASSA_TEST_SHOP_ID`, `YOOKASSA_TEST_SECRET_KEY` и один аккаунт владельца в `BILLING_TEST_ACCOUNT_IDS`; production требует отдельные `YOOKASSA_PRODUCTION_SHOP_ID` и `YOOKASSA_PRODUCTION_SECRET_KEY` и доступен всем активным аккаунтам. Нативный SDK может отдельно использовать тестовый магазин при веб-режиме production, не переключая сайт. Неполная или несогласованная конфигурация отклоняется при запуске. Интерфейс показывает условный либо реальный платёж по режиму конкретного заказа; способ оплаты не сохраняется и автосписаний нет.

Цена хранится в `billing.pricing` в целых копейках за монитор на календарный месяц (RUB). Миграция задаёт исходную цену 2900 копеек; последующие изменения выполняет администратор. `POST /api/v1/billing/orders` сначала сохраняет заказ и неизменяемый запрос, возвращает `201 pending`; worker создаёт платёж с ключом идемпотентности, равным ID заказа. `GET /api/v1/billing/orders/{id}` возвращает только состояние своего заказа из БД. `GET /api/v1/billing/orders?page=1&pageSize=10` возвращает `{orders,pagination:{page,pageSize,total,totalPages}}` для своего аккаунта, от новых заказов к старым (`created_at DESC,id DESC`); размер страницы ограничен 100, номер за пределами истории прижимается к последней странице. Legacy `GET /api/v1/billing` по-прежнему содержит до 100 последних заказов. Возврат браузера с платёжной страницы не подтверждает оплату. После сетевого сбоя повтор использует прежний заказ; если неизвестный результат CREATE не разрешён за 23 часа, требуется разбор без автоматического нового платежа. Известный payment ID продолжает сверяться через GET.

В кабинете ЮKassa указывается `https://api.heartbeat-checker.ru/webhooks/billing/yookassa` и события `payment.succeeded`, `payment.canceled`. Публичный маршрут принимает только ограниченный POST от адресов провайдера; данные webhook сохраняются в минимальный inbox. Перед выдачей доступа worker получает платёж через API и сверяет ID, неизменяемые режим и магазин заказа, связь с заказом, сумму, RUB и явный `payment.test`. Повторы не выдают квоту и не ставят отчёт повторно. Подтверждённый новый платёж меняет только подписку: действующая административная часть сохраняется и прибавляется к ней. Удалённый или неактивный аккаунт не восстанавливается. Исторические заказы со статусом `succeeded/blocked/admin_grant` остаются заблокированными и не применяются повторно. Источники тестовой и оплаченной квоты различаются: `yookassa_test` и `yookassa`. Оплаченная квота действует и после отключения новых платежей.

Включение выполняется workflow `Deploy backend` с отдельным `activate_yookassa_production=true`. Защищённые secrets environment `production-backend` передаются в приватный staging helper через stdin. Он меняет только billing provider, режим и два production-значения; test credentials и остальные строки `.env` сохраняются. Перед активацией helper проверяет выбранный магазин read-only GET `/v3/me`: точный ID, `test=false`, `status=enabled`. После остановки API/worker/probe предмиграционный gate запрещает смену магазина при незавершённых заказах, неопределённых операциях, webhook hints и leases; он ничего не отменяет и не перепривязывает. Production keys доступны только API/worker. Миграция `0022` расширяет режим заказа и источник квоты без изменения прежних записей. Новый заказ возвращает браузер на `/app`; обзор перечитывает квоту через backend, сам возврат не подтверждает оплату. Фактический выпуск и внешняя проверка записываются в `../context.md`. Настоящая оплата, возврат и отчёт требуют отдельной проверки на реальной операции. Чеки НПД формируются вручную в «Мой налог»; автоматизация чеков и автопродление не входят в этот этап.

### Нативный Android API и оплата через SDK

Нативный клиент авторизуется непрозрачным Bearer-токеном отдельной Android-сессии. Регистрация с шестизначным кодом, вход, сброс пароля и OAuth через Chrome Custom Tabs работают через `/api/v1/auth/native/*`; браузерные cookie и CSRF остаются на веб-маршрутах. OAuth link/unlink обновляет Bearer-токен в том же session ID, но сохраняет прежнюю revoke capability на весь срок этой сессии. Ответ после такой ротации не содержит `revokeToken`: клиент сохраняет уже защищённый revokeToken только при совпадении session ID. Публичный `POST /api/v1/auth/native/revoke` принимает `{sessionId,revokeToken}` и возвращает одинаковый `204` для повторного или неверного отзыва; этот секрет никогда не авторизует API-запросы.

`GET /api/v1/billing` возвращает `nativeCheckout:{enabled,shopId,environment,paymentMethods}`. Флаг `YOOKASSA_NATIVE_SDK_ENABLED` по умолчанию `false`; при включении обязателен `YOOKASSA_NATIVE_SDK_MODE=test|production`, одинаковый для API и worker. Для test используются существующие `YOOKASSA_TEST_SHOP_ID`, `YOOKASSA_TEST_SECRET_KEY` и единственный проверенный UUID в `BILLING_TEST_ACCOUNT_IDS`, даже если веб-магазин работает в production. Пока подтверждён только `BANK_CARD`, без сохранения способа оплаты и автосписания. Нативный Bearer и разрешённый магазин требуются для `POST /api/v1/billing/native/orders` с `{monitorCount,idempotencyKey,priceVersion,purchaseKind,packageId}`. Ответ `{order,sdk}` содержит серверную сумму в копейках, валюту, `shopId`, `environment=test|live` и срок котировки; `order.sdk` сохраняет те же магазин и среду для повторного открытия. Клиент сравнивает их со своей SDK-конфигурацией до токенизации. Заказ ждёт токен до 15 минут, не обращаясь к ЮKassa. Существующие веб-заказы и `returnTarget=android` для redirect checkout продолжают работать независимо.

`POST /api/v1/billing/native/orders/{id}/token` принимает только `{paymentToken,paymentMethodType:"BANK_CARD"}`. Один и тот же токен можно безопасно повторить; заменить его или использовать в другом заказе нельзя. Токен не возвращается и хранится только в зашифрованном неизменяемом запросе worker. `POST /api/v1/billing/native/orders/{id}/cancel` с `{}` отменяет только ещё не начатый draft. `GET /api/v1/billing/orders/{id}` показывает `checkoutKind` и `sdk.state`; подтверждение оплаты происходит только после сверки с API ЮKassa. Worker повторяет строго тот же запрос и ключ идемпотентности заказа не дольше 55 минут после draft, затем удаляет шифротекст. Неопределённый результат остаётся на ручной разбор без второго платежа; поздний webhook может восстановить только проверенный GET по payment ID.

Для локальной разработки сохранена отдельная БД `heartbeat_sdk_local` и запуск API/worker/probe на loopback. Локальный DB allowlist принимает только `heartbeat_local` и `heartbeat_sdk_local` на числовом loopback `:55432` с `sslmode=disable`; закрытые ключи находятся в игнорируемой `.local/yookassa-sdk/test.env` (`0600`). Проверка владельца на телефоне использует публичный HTTPS API и опубликованный APK с тестовым SDK-ключом; локальный API и USB для этого не нужны. Веб-магазин остаётся live. Тестовые платежи создают отдельные пакеты `yookassa_test`; продление live-пакета через тестовый SDK возвращает конфликт, а действующая live-квота не складывается с тестовой.

### Управление тарифом

Публичный `GET /api/v1/billing/pricing` возвращает `{pricing:{pricePerMonitorMinor,currency,period,version,updatedAt}}` с `Cache-Control: no-store`. Отсутствующая запись или ошибка БД — `503`, без резервной цены. `GET /api/v1/billing` также возвращает `priceVersion`. При недоступной текущей цене overview сохраняет историю и созданные заказы с их суммами и ссылками оплаты, возвращая `pricePerMonitorMinor=0, priceVersion=0`: это недоступная котировка, а не бесплатный тариф. Новый заказ без действующей цены закрыт; публичный pricing endpoint по-прежнему отвечает `503`. `POST /api/v1/billing/orders` требует `priceVersion` для нового заказа: устаревшая или отсутствующая версия даёт `409 price_changed`, после обновления суммы пользователь явно подтверждает заказ снова. Новый заказ ограничен 350000 рублями (`400 order_amount_exceeded`), без изменения старых заказов. Повтор прежнего `idempotencyKey` с теми же provider/count возвращает неизменённый заказ до проверки тарифа. Суммы старых заказов, запрос к провайдеру и оплаченные периоды не пересчитываются. При неопределённом исходе браузер сохраняет ключ, количество и исходную котировку; автоматического нового заказа нет.

Административные `GET/PUT /api/v1/admin/billing/pricing` используют существующий MFA-доступ; PUT требует свежего подтверждения и JSON `{pricePerMonitorMinor,version,reason}`. Цена — целое число 100–1000000 копеек, причина обязательна (до 500 байт). Конкурентное изменение — `409 version_conflict`. Изменение цены и событие `billing.pricing_updated` фиксируются одной транзакцией; журнал содержит actor/session, before/after, reason и `metadata.setting=monthly_monitor`, без привязки к аккаунту-получателю. Та же цена при актуальной версии не создаёт изменение.

### Локальная имитация оплаты

`BILLING_PROVIDER=mock` открывает в `/app/billing` демонстрацию расчета по текущему серверному тарифу. Деньги не списываются, реквизиты ЮKassa и карт не используются, автопродление не выполняется. Выдача тестовой квоты доступна только подтвержденным активным аккаунтам из `BILLING_MOCK_ACCOUNT_IDS`; пустой список запрещает ее всем. Для остальных аккаунтов демонстрация не создает заказ и не меняет квоту. Активная административная квота блокирует mock-заказ и его подтверждение; тестовая имитация не является оплатой и не заменяет реальную подписку. Mock не является пробным периодом или оплаченной подпиской.

Сервер проверяет стоимость, владение заказом, допустимый переход и idempotency key. Успешная симуляция атомарно меняет заказ, ограниченную по сроку квоту `mock_test` и очередь отчета. Повтор подтверждения не продлевает доступ. Продление действующей тестовой квоты разрешено только с прежним количеством мониторов; перерасчет и смена тарифа здесь не моделируются. При `BILLING_REPORTS_ENABLED=true` Informer отправляет отчет в отдельный payments-топик с пометкой «ТЕСТ — деньги не списывались». Ошибка доставки не отменяет результат заказа; статус, безопасный код ошибки и повторы хранятся отдельно.

### Ежедневные backup в S3

В отчёте Informer размер архива показывается в КБ/МБ. Подписанная ссылка на зашифрованный архив действует до семи дней, не дольше оставшегося окна хранения; срок хранения копий остаётся четырнадцать дней. Уже отправленные отчёты повторно не рассылаются.

Workflow `Backup backend` запускается из `master` ежедневно в 04:00 МСК; фактический старт GitHub schedule может задержаться. Отдельный запуск каждые 15 минут повторяет только ожидающие Telegram-отчеты. Ручной workflow принимает `run` или `report`. Backup использует установленный CI образ по immutable digest и проверяет OCI revision; общая VPS-блокировка исключает одновременную миграцию и резервирование.

Служебные операции релиза и backup реализованы в отдельном Go-модуле `tools` и собираются в статический `hc-ops` для Linux amd64 из точного source SHA. CI сохраняет контрольную сумму артефакта; deployment-скрипты проверяют её и встроенный SHA до первого запуска на VPS. Перед активацией backend-конфигурации workflow запускает ограниченную live-проверку нового S3-клиента в существующем backup-контейнере: исходный SHA тестового бинарника проверяется без сети и секретов, затем используются только два случайных объекта в отдельном префиксе. Проверка охватывает условную запись, чтение и SHA256, private ACL, multipart, подписанную ссылку и удаление обоих объектов; сбой блокирует релиз. Этот тест не заменяет ежедневную проверку восстановления архива.

Архив включает полный `pg_dump` прикладной БД `heartbeat`, ledger миграций и ключи восстановления: `WEBHOOK_ENCRYPTION_KEY`, `AUTH_MAIL_ENCRYPTION_KEY`, `SUPPORT_ENCRYPTION_KEY`, а после включения MFA — также `AUTH_MFA_ENCRYPTION_KEY`. Старые архивы с тремя ключами остаются пригодны для восстановления до появления MFA-данных. Архив шифруется age до загрузки в приватный S3. Рабочие DB/crypto-параметры берутся из канонического `.env`; отдельный `.backup.env` с правами `0600` содержит только `BACKUP_S3_*`, публичный `BACKUP_AGE_RECIPIENT` и Informer-токен/ID группы/backups-топика. Приватный age identity хранится у владельца вне VPS и Git. Его утрата делает долгосрочное восстановление невозможным.

Каждый запуск скачивает зашифрованный объект обратно, сверяет SHA256, расшифровывает временным проверочным ключом и восстанавливает dump в изолированный PostgreSQL без внешнего порта. Проверяются ключи и migration ledger. При первичной настройке отдельно требуется восстановление скачанного архива приватным ключом владельца; ежедневная проверка временным ключом его не заменяет. Открытые данные и временный ключ живут только в tmpfs. Результат сохраняется до отправки отчета, повтор отчета не создает новый dump.

S3 хранит ежедневные архивы 14 дней внутри собственного префикса `heartbeat-checker/production/daily/`; чужие объекты не удаляются. Telegram получает результат, размер, checksum и ссылку сроком до семи дней, не дольше оставшегося окна хранения, только на зашифрованный объект, без БД и ключей. Копии перед миграциями на VPS имеют отдельный жизненный цикл. На сервере с 2 ГБ RAM размер БД и память восстановления требуют наблюдения: tmpfs и restore могут исчерпать ресурс, поэтому наличие расписания не является доказательством достаточной емкости.

### Backend VPS и доставка

Отдельный VPS `176.12.64.115` и DNS `api.heartbeat-checker.ru` используются для Caddy, Go API, worker, изолированного probe и PostgreSQL 18.6. Публичные 80/443 нужны Caddy для HTTPS; API, PostgreSQL и probe не имеют опубликованных host-портов. Кроме защищённых секретами точных POST endpoint Support и Informer (тело не более 1 МБ), backend Caddy допускает к API только непосредственное соединение с frontend VPS `157.22.184.14`, остальные запросы получает `403`. Go принимает `X-Heartbeat-Client-IP` только от backend Caddy `172.30.64.2/32`, требует ровно один IP и не доверяет произвольным `X-Forwarded-For` и `Forwarded`. `AUTH_ORIGIN` остаётся `https://heartbeat-checker.ru`; браузер использует cookie и CSRF через публичный origin frontend. Наличие этой конфигурации и успешный технический деплой сами по себе не подтверждают сквозные сценарии регистрации и почты.

В Compose разделены edge-сеть Caddy/API, внутренняя сеть PostgreSQL/API/worker/migrate и сеть worker/probe. Probe получает только `PROBE_SHARED_SECRET`, не имеет доступа к БД, ключам шифрования и SMTP. Его IPv6 отключён; host-правила `DOCKER-USER` и `INPUT` ограничивают новый исходящий трафик публичными TCP 80/443 и DNS UDP/TCP 53 к указанным резолверам, запрещая частные, link-local, metadata и host-адреса. Код probe дополнительно проверяет каждый DNS-ответ и redirect. До запуска необходимо проверить эти ограничения из сетевого namespace probe на самом VPS; одного UFW для Docker недостаточно.

`deploy/backend/bootstrap.sh` рассчитан на чистую Ubuntu 22.04/24.04/26.04 amd64. Вместе с ним должен лежать `probe-firewall.sh`. Запуск от root с отдельным публичным SSH-ключом CI через stdin устанавливает Docker/Compose, пользователя `heartbeat-deploy`, каталог `/opt/heartbeat-checker/backend` и постоянные правила probe до автоматического старта контейнеров при перезапуске Docker. Существующие правила UFW и доступ SSH bootstrap не сбрасывает. Пользователь в группе Docker имеет административные права на выделенном VPS; его приватный SSH-ключ хранится только в GitHub secret.

Production-конфигурация находится только в `/opt/heartbeat-checker/backend/.env` с правами `0600`, не в Git. Обязательны `POSTGRES_PASSWORD`, `DATABASE_URL` для `heartbeat@postgres:5432/heartbeat` с тем же паролем, `TURNSTILE_SECRET_KEY`, `WEBHOOK_ENCRYPTION_KEY`, `AUTH_MAIL_ENCRYPTION_KEY`, `PROBE_SHARED_SECRET`, а для версии с административным MFA — отдельный `AUTH_MFA_ENCRYPTION_KEY` (строгий base64 от 32 байт). Также нужны `SMTP_ADDR`, `SMTP_FROM`, `SMTP_USERNAME`, `SMTP_PASSWORD` и `SMTP_TLS_MODE=implicit_tls|starttls`. Compose передает MFA-ключ только API и зашифрованному backup, не worker, probe или frontend. Ключи шифрования должны сохраняться вместе с backup БД, иначе зашифрованные webhook, ожидающие письма и факторы MFA не восстановятся.

Для workflow `Deploy backend` нужны repository variables `BACKEND_DEPLOY_HOST=176.12.64.115`, `BACKEND_DEPLOY_USER=heartbeat-deploy` и secrets `BACKEND_DEPLOY_SSH_KEY`, `BACKEND_DEPLOY_KNOWN_HOSTS`. Запуск вручную из `master` принимает полный `source_sha`, подтверждает его присутствие в master и успешный push-CI того же SHA. Workflow собирает `api`, `worker`, `probe`, `migrate`, `backup`, проверяет OCI revision, публикует пять immutable digest в GHCR и передает их по SSH на VPS; релизы сериализованы. Сам деплой выполняется только GitHub Actions, не прямой командой release по SSH.

Для включения Telegram relay в уже подготовленном backend `.env.next` выберите `activate_telegram_relay=true` при запуске `Deploy backend`; по умолчанию флаг выключен. Отдельный флаг `activate_messenger_notifications=true` разрешает включить Informer из того же полного `.env.next`; оба флага можно выбрать вместе. Скрипт под блокировкой принимает только обычный файл с правами `0600` и неизменные остальные строки `.env` вместе с комментариями и их порядком. Для relay разрешены только точные `TELEGRAM_API_BASE_URL` и `TELEGRAM_API_PROXY_IP`; для Informer — `MESSENGER_NOTIFICATIONS_ENABLED=true`, два отдельные webhook-секрета, новый MAX-токен и публичные адреса ботов. Существующий `TELEGRAM_BOT_INFORMER_TOKEN`, который используют платежные отчёты и резервное копирование, обязан остаться прежним. Проверка и применение используют одни и те же байты подготовленного файла; перед удалением скрипт снова убеждается, что `.env.next` не изменился. Если оба флага выключены, `.env.next` не применяется. До начала миграции ошибка восстанавливает прежнюю `.env`; если сам возврат не удался, защищённый снимок и блокирующий `pending` остаются для восстановления. После начала миграции действующая конфигурация и `pending` остаются для исправления вперёд. После всех проверок `.env.next` удаляется, а обе активации записываются в receipt без секретов.

Версия с административным MFA требует ключ до запуска API. Флаг `activate_admin_mfa=true` в том же workflow разрешает добавить только ранее отсутствующий или пустой `AUTH_MFA_ENCRYPTION_KEY` из полного `.env.next`; замена действующего ключа отклоняется. Скрипт сравнивает остальные байты `.env` без вывода секретов и проверяет, что worker/probe не получают MFA-ключ. Флаг `provision_owner=true` запускает после миграции `0012` и проверенного pre-migration backup отдельную create-only транзакцию из защищённого `.owner-import.next.json` (обычный файл `0600`) и SQL текущего `source_sha`. Payload передаётся PostgreSQL через stdin в hex-виде, не через аргументы или CI-журнал. Транзакция создаёт профиль, существующий Argon2id hash, квоту `admin_grant` и неизменяемый audit-маркер; конфликт UUID/email останавливает выпуск без перезаписи. Повтор того же payload сверяется с маркером в БД и не возвращает старые пароль, роль или квоту после последующих законных изменений. Локальный `receipts/owner-import.json` служит зеркалом маркера, а не источником идемпотентности; staged payload удаляется только после readiness и проверки неизменности байтов.

Вход через Яндекс и VK включается отдельным `activate_oauth=true` в `Deploy backend` после подготовки полного `.env.next` на VPS. Разрешены только `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI`, `YANDEX_SCOPES`, `VK_CLIENT_ID` и `VK_CALLBACK_URL`; уже заданные непустые значения нельзя заменить в этом режиме. Callback должны точно совпадать с `https://heartbeat-checker.ru/api/v1/auth/oauth/{provider}/callback`, scopes Яндекса — `login:email login:info`. Эти параметры получает только API; `VK_SERVICE_TOKEN` и `YANDEX_SUGGEST_HOSTNAME` для этого входа не используются и через workflow не переносятся. Два точных callback-пути frontend Caddy отправляет прямо в backend edge, минуя Next proxy; чувствительные query-поля исключены из Caddy logs. Остальные маршруты идут прежним путём. Флаг по умолчанию выключен, успешная активация отражается в receipt без значений конфигурации. Live-вход у самих провайдеров владелец проверит отдельно после публикации.

Relay на `messengers-proxy.heartbeat-checker.ru` принимает точный POST webhook Telegram Informer и пересылает его на backend с проверкой TLS. Его собственные upstream для Telegram API и backend разрешаются через runtime DNS (`1.1.1.1`, `8.8.8.8`), чтобы временная ошибка DNS при старте nginx не требовала перезапуска relay. Метод, URI, размер тела, заголовки, TLS-проверка и allowlist исходящего Telegram API остаются ограниченными конфигурацией relay.
Отдельные nginx snippets AeroCRM по-прежнему используют разрешение DNS при старте и могут ограничить полный перезапуск общего nginx при недоступности их upstream.

Скрипт деплоя сверяет адрес БД и SMTP TLS mode, поднимает PostgreSQL, останавливает пишущие процессы, создаёт локальный `pg_dump` и пробно восстанавливает его в отдельную временную БД. Затем он сохраняет прежние Compose/Caddy/release-файлы и защищённую `.env` в `recovery/`, записывает `pending` с путем к backup и применяет миграции отдельным контейнером. Миграции используют checksum ledger, advisory lock и одну транзакцию. После них проверяются API readiness, authenticated probe GET собственного сайта, запрет metadata-адреса, стабильный worker, действующий TLS и запрет постороннего доступа к backend edge. Успешный релиз оставляет локальный JSON receipt с SHA, digest, backup checksum и числом миграций; backup не публикуется как artifact CI.

До начала миграции ошибка возвращает предыдущие файлы и процессы. После начала миграции скрипт сохраняет `pending`, backup, recovery snapshot и текущие файлы для проверки и исправления вперёд; автоматического возврата старых бинарников после DDL нет. Ни один сценарий не удаляет PostgreSQL volume. Успешный технический деплой подтверждает процессы и контракты, но не реальную регистрацию, доставку письма адресату, платёж или приемку мониторинга под нагрузкой. Frontend переключается в `app` отдельным workflow только после успешного backend-деплоя и необходимых проверок.

На этой машине LuLu задерживал первое внешнее соединение каждого нового временного Go-бинарника. После временного отключения LuLu пользователем полный live smoke прошел. При повторении таймаута нужно проверить разрешение конкретного Go-процесса в локальном сетевом фильтре; таймаут Siteverify и проверка TLS в коде не ослаблялись.

### Принятые решения

- Весь backend, включая уже работающие регистрацию, вход, сессии, проверки и права, пишется на Go; платежи запланированы здесь же
- Frontend - Next.js с архитектурой Feature-Sliced Design (FSD). Реализованы лендинг, личный кабинет и административный интерфейс `/app/admin`
- Пользовательские сценарии входа, кабинета и управления пользователями берем за образец из aeroCRM и адаптируем под мониторинг
- Better Auth и Keycloak в стартовую архитектуру не входят
- Капча - Cloudflare Turnstile. Токен проверяет Go-backend
- Email и пароль остаются способом входа; Яндекс и VK доступны после отдельной активации OAuth-конфигурации
- Настройки и управление находятся на сайте. Telegram и MAX используются для уведомлений и привязки получателя
- Каналы уведомлений - Telegram, email и MAX
- Android-приложение открывает обновляемый с сайта кабинет; подписанный APK публикуется через CI, подготовка и модерация RuStore выполняются отдельно
- Цена за монитор в месяц задаётся администратором и показывается до заказа. Пользователь оплачивает квоту из N мониторов и может заменять URL внутри нее
- Оплата через ЮKassa. Доступны новая покупка пакета и ручное продление выбранного пакета; автопродление отложено
- Пробного периода нет. Проверки запускаются в пределах оплаченной квоты
- Каждый новый пакет действует отдельный календарный месяц с момента активации оплаты. Можно купить дополнительные места в любой день или продлить выбранный пакет в прежнем размере. Активные пакеты и административные места складываются
- При истечении пакета доступная квота уменьшается на его места, остальные пакеты и административная квота продолжают действовать. Кабинет и сохранённая история остаются доступны
- Для каждого монитора пользователь задает интервал 1–10 минут (для новых по умолчанию 5) и порог 1–10 последовательных неудачных проверок (по умолчанию 2). Первая успешная проверка закрывает инцидент
- Подробные результаты хранятся 7 дней. Инциденты и сводная статистика - 90 дней
- В режиме `frontend` сайт показывает интерфейс без backend и не проводит операции с аккаунтами; режим `app` подключает Go API

### Основной подход

Модульный монолит на Go: одна кодовая база и один `go.mod`, разделенные на бизнес-модули с явными границами. Модули вызывают публичные контракты друг друга или обмениваются сохраняемыми событиями. HTTP между бизнес-модулями внутри процесса не нужен.

Из одной кодовой базы собираются три работающих процесса: `api` обслуживает сайт, `worker` планирует проверки и очищает данные, `probe` обращается к проверяемым публичным адресам. Такое разделение позволяет ограничить доступ исполнителя проверок и отдельно управлять его нагрузкой.

| Компонент | Ответственность |
| --- | --- |
| Next.js | Страницы, формы, отображение данных и серверный рендеринг интерфейса |
| Reverse proxy | HTTPS на frontend и backend, маршрутизация same-origin `/api/v1/*` и проверка источника межсерверного запроса |
| `api` | HTTP API, аутентификация, права и пользовательские операции; входящие webhook поддержки Telegram/MAX |
| `worker` | Планирование проверок, обработка результатов и инцидентов, очистка истории, исходящие webhook и production-очередь писем auth; остальные доставки и продления запланированы |
| `probe` | Ограниченное выполнение запросов к пользовательским адресам |
| PostgreSQL | Данные приложения, сессии, задания, результаты, события и учет доставок |

Для старта используется PostgreSQL без Redis и отдельного брокера сообщений. Сохраняемые задания и transactional outbox обеспечивают восстановление фоновой работы после перезапуска. Outbox — запись события в той же транзакции, что и изменение бизнес-данных; в этой же транзакции для настроенного webhook создается доставка.

Отдельный API Gateway не нужен. Маршрутизация остается в reverse proxy, а проверка сессий и прав - в Go. Выделение новых сервисов или брокера рассматривается при измеримой потребности в независимом масштабировании, изоляции или пропускной способности.

Для деплоя пользователь выбрал размещение frontend на отдельном сервере. Next.js и публичный reverse proxy обслуживают `heartbeat-checker.ru`, а `/api/v1` проксируется к Go API на backend-сервере с worker, probe и PostgreSQL. Браузер продолжает использовать один origin; правила cookie, Origin и CSRF остаются в Go. Bootstrap backend VPS и CI/CD-манифесты находятся в `deploy/backend`; результаты конкретных релизов и приемки записываются в корневом `../context.md`.

Публичные `AUTH_ORIGIN` и `WEB_PUBLIC_ORIGIN` должны совпадать с `https://heartbeat-checker.ru`. Proxy передает `Origin`, `Cookie`, `Set-Cookie` и `X-CSRF-Token`, не кэшируя API/auth. Подготовленный межсерверный канал использует HTTPS с проверкой сертификата; PostgreSQL и probe не публикуются. `GO_API_ORIGIN` закрепляется в rewrites при сборке Next.js, поэтому смена upstream требует пересборки frontend. Передача клиентского IP ограничена frontend Caddy, backend Caddy и точным доверенным адресом в Go.

Краткие результаты действий на сайте отображаются через `shared/notifications` и `react-hot-toast`: успех на 4 секунды, ошибка на 6 секунд, с возможностью закрыть уведомление. Общий renderer сохраняет таймеры при смене страницы и диалога; визуальный слой поднимается поверх открытого native dialog. Валидация, ошибки загрузки с повтором, неизвестный результат операции и одноразовые секреты остаются рядом с соответствующим интерфейсом. React Native-приложение показывает собственные сообщения и отдельно запрашивает разрешение Android на push для инцидентов.

Главная и оферта получают текущий тариф сервером при каждом запросе и обновляют его в открытой вкладке; при недоступности API числовая цена скрыта. mock-оплата в кабинете обозначена как тестовая. Состояния — успешная проверка, первая ошибка, повторная ошибка с открытием инцидента и восстановление. Доступны пауза и ручной выбор шага; автопроигрывание останавливается вне экрана и в скрытой вкладке, а при `prefers-reduced-motion` не запускается. Содержательный текст и FAQ рендерятся сервером; интерактивная демонстрация находится внутри слайса `_pages/home` и не обращается к API.

Маршруты Next.js находятся в `apps/web/app`, а FSD-код - в `apps/web/src`. Слои App и Pages называются `_app` и `_pages`, чтобы не конфликтовать с особыми каталогами Next.js. Файл маршрута подключает готовую страницу, сам интерфейс находится в соответствующем слайсе. [FSD и Next.js](https://feature-sliced.design/docs/guides/tech/with-nextjs)

Порядок зависимостей: `_app > _pages > widgets > features > entities > shared`. Код импортирует нижние слои. Слайсы одного слоя изолированы, например `features/create-monitor` не импортирует `features/delete-monitor`. Их взаимодействие собирается на уровне страницы или виджета. [Слои FSD](https://feature-sliced.design/docs/reference/layers)

- Слайс называется по своему назначению. Например, `features/create-monitor` или `entities/incident`
- Внутри слайса используются нужные сегменты: `ui`, `model`, `api`, `lib`. Пустые сегменты не создаются
- Между слайсами используются явные публичные экспорты `index.ts`. Импорт внутренних файлов чужого слайса не допускается
- `shared/ui` не знает о мониторах и подписках. `shared/api` содержит общий транспорт, а запросы конкретной сущности находятся в ее слайсе
- Server-only код имеет отдельный публичный вход, если слайс используется и серверными, и клиентскими компонентами. Он не попадает в клиентский bundle
- Next.js отвечает за интерфейс и его рендеринг. Авторизация, платежные решения, права и бизнес-правила выполняются Go API
- Границы слоев и слайсов проверяются frontend-линтером. Реализованы лендинг, формы auth, кабинет, управление мониторами, тестовая оплата и административный интерфейс

### Правила модулей и читаемости кода

- `domain` не импортирует SQL, HTTP, провайдеров или соседние модули
- `service` описывает сценарий. Интерфейс зависимости определяется там, где он нужен, без интерфейса на каждый тип
- HTTP-обработчик проверяет формат запроса, вызывает сценарий и формирует ответ. SQL и бизнес-правила в обработчик не помещаются
- Репозиторий отвечает за хранение. Решения о тарифе, доступности сайта и правах остаются в прикладных сценариях и домене
- Каждый модуль владеет своими таблицами. Чтение и изменение чужих таблиц через собственный SQL не допускаются
- Для вызовов другого модуля используются `contracts`. Закрытые доменные типы и репозитории наружу не выдаются
- `module.go` собирает реализацию и предоставляет контракты и HTTP-обработчики. Только `app` связывает модули между собой
- Вложенный `internal` запрещает импорт реализации соседним модулем и пакетом `app`. `app` получает доступ через `module.go`
- `contracts` не зависит от собственного закрытого `internal`. Циклических импортов и обратной зависимости `platform` от модулей нет
- Зависимости передаются обычными конструкторами. Глобальные сервисы, скрытый service locator и DI-фреймворк не нужны
- `platform` содержит технические механизмы без бизнес-правил. Общий `pkg` и универсальные `helpers` заранее не создаются
- Функции имеют понятные имена и одну задачу. Комментарии объясняют причину решения или ограничение, а не пересказывают строку кода
- Ошибки возвращаются явно и сохраняют причину. Контекст отмены и таймаут передаются через `context.Context`
- Деньги хранятся в целых копейках. Цена одного монитора хранится в `billing.pricing`, вычисления через `float64` не используются
- Транзакции короткие. HTTP-запросы к проверяемым сайтам и провайдерам выполняются после освобождения блокировок БД
- `gofmt`, статический анализ и тесты значимых сценариев выполняются при разработке. В первую очередь проверяются границы доступа, конкурентные операции, повторы и восстановление после ошибок

### Авторизация и пример aeroCRM

Модуль `auth` реализован на Go. Формы Next.js обращаются к Go API через proxy того же origin. Авторизация проверяет роль и состояние аккаунта; доступ к мониторам ограничен владельцем и действующей квотой.

Из aeroCRM берем сценарии регистрации по email с подтверждением, входа по паролю, редактирования профиля, смены пароля, просмотра и отзыва сессий. Административный интерфейс управляет аккаунтами, квотами и мониторами и показывает журнал действий; управление платежами, инцидентами и состоянием доставок в него пока не входит.

Проверенные исходники aeroCRM: локальный checkout `sales-productivity-release`, commit `ef37faa9785b67b4e91effeaea01af4971015ca3`. Основные ориентиры - `identity/src/auth/auth.service.ts`, `CabinetPageClient.tsx` и `admin-navigation.data.ts`. Это проверка исходников, а не новая проверка production.

Для браузера реализованы серверные сессии в PostgreSQL и непрозрачный случайный идентификатор в `HttpOnly` cookie. В режиме HTTPS cookie имеет `Secure`, изменяющие операции защищены от CSRF. В БД хранится хеш идентификатора сессии. Каждый вход создает новую сессию, выход и отзыв делают ее недействительной. Административное изменение роли или статуса аккаунта отзывает все его сессии.

Пароли хешируются через `golang.org/x/crypto/argon2`. Подтверждения email и восстановления одноразовые, ограничены сроком и числом попыток. Восстановление дает установить новый пароль после проверки владения email. Сценарий отправки временного пароля из aeroCRM не переносится. Административный доступ требует включённой TOTP MFA и свежего подтверждения для изменений.

SMS и правило одной активной сессии из aeroCRM не включаются автоматически. Вход через Яндекс и VK реализован отдельно от aeroCRM и включается только после активации защищённой конфигурации. Публичная регистрация не позволяет назначить себе административную роль.

Cloudflare Turnstile защищает формы регистрации, входа и запроса восстановления. Go вызывает Siteverify и проверяет результат, ожидаемые hostname и action. Капча дополняет ограничения попыток, а не заменяет их. Истекший или повторно использованный токен не принимается. Для локальной разработки используются официальные тестовые ключи в отдельной конфигурации. [Проверка на сервере](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [локальное тестирование](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)

#### Локальный контракт auth/accounts

Все маршруты начинаются с `/api/v1`. Для JSON-запросов нужен `Content-Type: application/json`. Неизвестные поля, включая попытку передать роль при регистрации, отклоняются. Изменяющие запросы требуют точного `Origin`, указанного в `AUTH_ORIGIN`; после входа дополнительно нужен `X-CSRF-Token`. HTTP-клиент сохраняет cookie из ответа на вход.

| Метод и маршрут | JSON / результат |
| --- | --- |
| `POST /auth/registration` | `{email,name,password,turnstileToken}`; `202 {challenge}`, отдельная cookie попытки и письмо с кодом |
| `GET /auth/registration` | Собственная попытка по cookie: `{challenge}` либо `{challenge:null}` |
| `POST /auth/registration/{id}/resend` | `{turnstileToken}`; `202 {challenge}` после ограничения отправки |
| `POST /auth/registration/{id}/confirm` | `{code,turnstileToken}`; создание аккаунта и сессии, cookie и `{csrfToken,account}` |
| `POST /auth/register` | Совместимость старого клиента: `{email,name,password,turnstileToken}`; пустой `202`, письмо со ссылкой |
| `POST /auth/verify` | Совместимость старой ссылки: `{token,password}`; подтверждение email, `204` |
| `POST /auth/login` | `{email, password, turnstileToken}`; cookie, `{csrfToken, account}` |
| `GET /auth/csrf` | `{csrfToken}` для действующей cookie-сессии |
| `GET /me` | Текущий профиль, включая `hasPassword` |
| `PATCH /me` | `{name}`; обновленный профиль |
| `GET /me/sessions` | Последние 100 активных сессий текущего аккаунта |
| `DELETE /me/sessions/{id}` | Отзыв своей сессии, `204` |
| `DELETE /me/sessions` | Отзыв всех своих сессий и ранее выданных reset-токенов, `204` |
| `POST /auth/logout` | Выход и удаление cookie, `204` |
| `POST /auth/password/change` | `{currentPassword, newPassword}`; смена пароля и отзыв сессий, `204` |
| `POST /auth/password/reset/request` | `{email, turnstileToken}`; одинаковый `202` для существующего и неизвестного email |
| `POST /auth/password/reset/confirm` | `{token, password}`; новый пароль и отзыв всех сессий, `204` |
| `GET /auth/oauth/providers` | Доступность входа через Яндекс и VK |
| `POST /auth/oauth/{provider}/start` | `{mode:"login",returnTo?}` или `{mode:"link",password}`; URL авторизации провайдера |
| `GET /auth/oauth/{provider}/callback` | Проверка ответа провайдера и переход к входу, привязке или подтверждению email |
| `GET /auth/oauth/registration` | Данные ожидающей регистрации в этом браузере |
| `POST /auth/oauth/registration/confirm` | `{token}`; подтверждение email, создание аккаунта и сессии |
| `GET /me/identities` | Подключённые способы входа без внешних идентификаторов |
| `DELETE /me/identities/{provider}` | `{identityId,password}`; отключение с проверкой актуальной привязки |

Новый пользователь Яндекса или VK подтверждает email из письма в том же браузере; до этого аккаунт не создаётся. Если провайдер не передал email, используется обычная регистрация с последующей привязкой в настройках. Совпадение email с существующим аккаунтом не связывает его автоматически: сначала нужно войти существующим способом, затем подключить провайдера в настройках с текущим паролем. Администратору дополнительно требуется свежая MFA-проверка. Отключение последнего способа входа без пароля запрещено. У OAuth-аккаунта без пароля форма настроек ведёт к установке пароля через письмо восстановления. Привязка и отвязка отзывают другие сессии; текущая cookie обновляется. Код, state и device_id в callback не должны попадать в access logs.

Обычная регистрация проходит в два шага: имя, email и пароль → шестизначный код из письма. Аккаунт, подтверждённые учётные данные и сессия создаются атомарно только после верного кода; затем открывается кабинет. Отдельная HttpOnly cookie привязывает попытку и сохранённый хеш пароля к браузеру. Один ID или код из чужой попытки не позволяет подтвердить заранее заданный другим человеком пароль. Пароль и код не хранятся в browser storage и не передаются в URL; после перезагрузки этап восстанавливается по cookie. При неизвестном результате подтверждения интерфейс проверяет состояние GET-запросами и не повторяет POST автоматически.

Код действует 10 минут от начала попытки, повторная отправка — не раньше чем через 60 секунд. Повтор не продлевает срок и не сбрасывает пять допустимых неверных попыток; действует только последнее письмо. Для уже занятого email ответ сохраняет тот же формат, но новый аккаунт, сессия и письмо не создаются. Новая регистрация не меняет существующие права или пароль и выдаёт роль `user` с квотой 0. Старые ссылки продолжают требовать исходный пароль и отдельный вход после подтверждения; OAuth-сценарий сохраняется.

Пароль хранится как Argon2id с отдельной случайной солью: 19 MiB памяти, две итерации, один поток. [Рекомендации OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Cookie содержит случайный токен, БД — его SHA-256, отдельный публичный ID сессии и версию учетных данных. Вход и изменение пароля сериализуются по учетной записи. Сброс/смена пароля отзывает ранее открытые сессии; повторное применение токена не допускается.

По умолчанию сессия действует 30 дней, старые ссылки подтверждения email и сброса пароля — 30 минут, новые шестизначные коды — 10 минут. Cookie имеет `HttpOnly`, `SameSite=Lax`, `Path=/`; для HTTPS — `Secure` и имя с префиксом `__Host-`. HTTP с незащищенной cookie разрешен только локально. Смена пароля и повторный вход требуют получения нового CSRF-токена. В production `AUTH_SESSION_TTL=720h`; API доверяет клиентскому IP из `X-Heartbeat-Client-IP` только от точного адреса backend Caddy из `TRUSTED_PROXY_CIDRS`. Без доверенного соединения или с некорректным заголовком API отказывает; `X-Forwarded-For` и `Forwarded` не используются для ограничений попыток.

Имя: 2–100 символов после удаления крайних пробелов; пароль: 12–1024 байта, без обрезки и скрытого изменения. Параллельно выполняются не более двух вычислений Argon2id; при насыщении API возвращает `503`. Регистрация и запрос восстановления ограничены пятью запросами на email и двадцатью на IP в час. Вход — десять попыток на email и сто на IP за 15 минут; подтверждение и завершение сброса — двадцать на IP за 15 минут. Для одной заявки подтверждения допустимо пять неверных паролей. Смена пароля — десять попыток на аккаунт и двадцать на IP за 15 минут. Превышение лимита дает `429`; неверная сессия — `401`; отказ Origin/CSRF/капчи — `403`. Тело ошибки: `{ "error": "код" }`, без данных БД и провайдера.

`make check` не требует БД и внешних провайдеров. Интеграционные тесты включаются через `HEARTBEAT_TEST_DATABASE_URL`; защита в тестах допускает только проектную PostgreSQL на `127.0.0.1:55432`. Каждый тест создает отдельную БД и удаляет ее после завершения. Live smoke дополнительно включается через `HEARTBEAT_LIVE_AUTH=true`, отправляет письма на уникальный адрес `example.test` в Mailpit и удаляет только собственные сообщения. Пароли, cookie и токены из писем не выводятся в успешном отчете теста.

Для ручной проверки нового сценария откройте `/register`, запустив API и worker, и возьмите код из Mailpit. Следующий запрос проверяет совместимость старого API регистрации со ссылкой (Origin сайта соответствует `AUTH_ORIGIN`):

```sh
curl -i http://127.0.0.1:8080/api/v1/auth/register \
  -H 'Origin: http://127.0.0.1:3000' \
  -H 'Content-Type: application/json' \
  --data '{"email":"demo@example.test","name":"Demo","password":"local-demo-password-2026","turnstileToken":"XXXX.DUMMY.TOKEN.XXXX"}'
```

Письмо доступно в Mailpit: `http://127.0.0.1:58025`. Ссылки из писем ведут на работающие формы Next.js `/verify-email` и `/reset-password`; доступны также `/register`, `/login` и `/forgot-password`. При ручном обращении к API токен из письма передается в JSON `/auth/verify` вместе с паролем.

`TURNSTILE_LOCAL_TEST_MODE=true` допускает только официальные тестовые ключи и `XXXX.DUMMY.TOKEN.XXXX`, но каждый раз вызывает Cloudflare. Живой тестовый ответ проверяется по `metadata.result_with_testing_key`; hostname/action в этом режиме не отражают реальную форму. В обычном режиме требуются точные hostname и action. Локальный тестовый режим допускается только при loopback-адресах API и сайта; внешняя сеть нужна даже для локального smoke. Тестовые ключи не доказывают работу настоящего браузерного challenge: проверка с реальным виджетом и собственными ключами остается частью подготовки публичного запуска.

Для публичного сайта нужны `TURNSTILE_HOSTNAME=heartbeat-checker.ru`, `AUTH_ORIGIN=https://heartbeat-checker.ru`, secure cookie и выключенный локальный тестовый режим. Виджет Turnstile использует action `register`, `registration_resend`, `registration_confirm`, `login` или `reset`; Go API получает `turnstileToken` и проверяет action в ответе Siteverify. Работу настоящего виджета и Siteverify с production-ключами требуется проверить отдельно.

Служебные письма регистрации, подтверждения OAuth-регистрации и установки пароля используют фирменные русскоязычные Go-шаблоны: текст и HTML с логотипом, кнопкой, запасной ссылкой и сроком действия. Данные экранируются стандартными шаблонизаторами; JavaScript и отслеживания открытий нет. SMTP отправляет `multipart/alternative`, сначала текст, затем HTML. Старые задания очереди без HTML продолжают отправляться как текст; схема БД и ключ шифрования очереди не меняются. Это оформление auth-писем, а не реализация email-уведомлений об инцидентах.

Локальный и production API сохраняют зашифрованное задание письма в PostgreSQL в одной транзакции с challenge или reset-токеном. Локальный worker доставляет его в loopback Mailpit. Production worker забирает задания с lease, отправляет по SMTP с проверкой сертификата и аутентификацией только после TLS, повторяет временные ошибки ограниченное число раз и сохраняет статус окончательной ошибки. Тело письма удаляется из задания после успеха или окончательного отказа; письмо может продублироваться, если SMTP принял его, а ответ потерялся. `AUTH_MAIL_ENCRYPTION_KEY` обязателен для новых кодов в API и worker и должен переживать восстановление БД. Совместимый локальный режим без ключа допускает только прежние сценарии с прямой доставкой в Mailpit. Проверка SMTP-соединения и отдельного письма не заменяет сквозную приемку регистрации, подтверждения и восстановления через публичный сайт. Административная TOTP MFA реализована отдельно от почтовой очереди; регистрация не выдает административных прав. Оставшиеся ограничения записаны в корневом `../backlog.md`.

### Проверки и инциденты

Один монитор выполняет один выбранный тип проверки. Типы используют общую квоту, интервал, порог сбоев, историю и доставку уведомлений; автоматического переключения между протоколами нет.

| Тип | Что указывать | Что означает успех |
| --- | --- | --- |
| `http` — сайт или API | `https://example.com/health`, GET/HEAD, ожидаемый HTTP-код; текст для GET необязателен | Ответ соответствует заданному коду и тексту |
| `tcp` — доступность порта | Публичный IPv4 или домен, например `server.example.com`, и один порт `22` | TCP-соединение установлено; исправность самого приложения этим не подтверждается |
| `icmp` — ответ сервера на пинг | Публичный IPv4 или домен без протокола и порта | Получен соответствующий ICMP Echo Reply; сервер может блокировать ICMP и при этом обслуживать другие запросы |

В HTTP режиме доступны GET/HEAD, ожидаемый код и поиск текста в теле GET; пользовательские заголовки остаются целевым расширением. Несколько условий для одного ответа не образуют дополнительные мониторы. По целевому тарифу повторные проверки и уведомления входят в стоимость.

Для HEAD проверка тела не применяется. Поддержка POST и сложных условий JSON добавляется отдельным сценарием, если нужна. Это техническое ограничение первой реализации, а не дополнительный тариф.

Действующий API под `/api/v1` предоставляет `GET/POST /monitors`, `GET/PATCH/DELETE /monitors/{id}`, `GET /monitors/{id}/results`, `GET /monitors/{id}/incidents` и `GET /entitlement`. Изменения требуют сессии, точного Origin и CSRF-токена. История результатов и инцидентов видна только владельцу монитора. Ответ инцидента содержит `closeReason`: `recovered` после успешной проверки, `config_changed` при изменении настройки, `paused` при остановке и `deleted` при удалении. Это различает восстановление проверяемого ресурса и прекращение наблюдения.

`GET /api/v1/monitors?page=1&pageSize=25&sort=created_desc&q=...` включает серверный поиск и страницы. `page` — от 1, `pageSize` — 1–100; сортировка: `created_desc` (по умолчанию), `created_asc`, `name_asc`, `name_desc`, `problems_first`. Фильтр `status=all|UP|DOWN|UNKNOWN|PAUSED|SUBSCRIPTION_REQUIRED|problems` применяется ко всему аккаунту до пагинации. `problems` включает DOWN, UNKNOWN и SUBSCRIPTION_REQUIRED; `problems_first` ставит эти состояния перед UP и PAUSED, внутри группы — новые первыми. Поиск — буквальное вхождение в имя или адрес без учёта регистра; после trim допускается до 200 символов Unicode. Неверные и повторяющиеся параметры возвращают 400. Ответ содержит `monitors`, `pagination: {page,pageSize,total,totalPages}`, `summary: {total,up,down,unknown,paused,subscriptionRequired}` и `asOf`: pagination.total учитывает поиск и статус, summary охватывает все мониторы аккаунта независимо от фильтров. `asOf` — единый момент расчёта свежести, фильтра и сводки. Пустая выборка имеет страницу 1; слишком большая страница сдвигается к последней доступной. Квота ранжирует только включённые мониторы по исходной дате создания и ID, независимо от поиска и сортировки; мониторы на паузе сохраняются без занятого места. Без параметров сохранены прежний `{monitors}` и порядок от старых к новым.

`GET /api/v1/monitors/{id}/statistics?days=7|30|90` (по умолчанию 7) возвращает `{statistics}` из сохранённых суточных агрегатов за календарные дни UTC: начало первого дня → `generatedAt`, последний день помечен `partial`. Это доля успешных **принятых проверок** (`successfulCheckPercent = 100 × UP / (UP + DOWN)`), а не доля времени доступности, SLA или полнота расписания. UNKNOWN учитывается отдельно и не входит в знаменатель; без UP/DOWN процент равен `null`. `averageLatencyMs` делит сохранённую сумму на `latencySampleCount`, без UNKNOWN; это общая длительность исторических проверок разных типов, а не ICMP RTT или p95. Данные RTT остаются в истории подробных результатов за 7 дней.

Ответ статистики содержит `monitorId, generatedAt, timeZone: "UTC", periodDays, from, to, methodology: "accepted_checks_v1", retentionDays: 90`, `coverage: {kind: "recorded_checks", firstRecordedDay, daysWithData, scheduleCompleteness: "unknown"}`, `totals` и все выбранные `days`. Счётчики: `up, down, unknown, total, successfulCheckPercent, averageLatencyMs, latencySampleCount`; у дня также `date` и `partial`. Дни без записей имеют нулевые счётчики и `null` измерения; отсутствие записей не означает 0% доступности. Покрытие относится к выбранному периоду, не доказывает работу до первой записи или непрерывность расписания; текущий интервал не позволяет восстановить прошлое ожидаемое число проверок. Срок хранения агрегатов не расширен. История доступна владельцу и при истёкшей квоте; чужой монитор →404.

`GET /api/v1/incidents?state=all|active|closed&limit=25&cursor=...` — общая лента владельца, по убыванию `openedAt,id`, до 100 записей за запрос. Ответ `{incidents, pagination: {limit,nextCursor,hasMore}, asOf}`; запись включает прежние поля инцидента, `monitorId` и текущую подпись `monitor: {id,name,checkType,target,timeZone}`. Курсор непрозрачен для клиента и связан с фильтром и первым `asOf`; сервер всегда берёт владельца из сессии. Новые подтверждения после `asOf` не попадают на следующие страницы, а закрытие и причина показываются на этот момент. Активный инцидент старше 90 дней остаётся доступным, закрытые имеют прежний retention 90 дней. Удаления и retention не дают гарантии неизменяемого снимка между запросами. Дубли параметров и неизвестные поля/значения отклоняются; прежние endpoints истории одного монитора сохранены.

Явная кнопка проверки push в Android использует `POST /api/v1/push/native/tests` с `{requestId: UUID}` и `X-Heartbeat-Installation-Credential` поверх штатной Android-сессии. Новая заявка →202, точный повтор →200; повтор requestId с другой установкой/сессией/привязкой →409. Проверка независима от квоты и наличия монитора, направлена только текущей установке и не принимает произвольных адресатов или текста. Лимиты: новая заявка раз в 60 секунд на установку и 5 в час на аккаунт; 429 содержит точные `Retry-After` и `nextAllowedAt`. TTL — 5 минут, максимум 3 внешних попытки с одним ID и закреплённым маршрутом. Ответ и `GET /api/v1/push/native/tests/{id}`: `{test:{id,state,createdAt,expiresAt,nextAllowedAt,receivedAt,displaySubmittedAt,errorCode}}`. Состояния: `queued`, `sending`, `provider_accepted`, `received`, `display_submitted`, `failed`, `expired`, `cancelled`. Принятие провайдером не означает получение телефоном.

Тесты используют отдельную таблицу `push_test_deliveries` миграции 0029, те же sender/шифрование/session guards и общий лимит двух внешних аренд с инцидентами; старые v1 задания не меняются. Opaque envelope v2 содержит только `v,deliveryId,installationId,bindingGeneration,expiresAt`. Установка читает `/api/v1/push/installation/test-deliveries/{id}` со своим Bearer credential: фиксированные `deliveryId,kind:"test",occurredAt,expiresAt,title,body,receiptToken`. Чтение контента не является квитанцией. Установка отдельно отправляет POST `.../{id}/receipt` с `{receiptToken,stage:"received"|"display_submitted"|"display_failed"}`; `display_submitted` — только после успешного вызова Android NotificationManager, без обещания, что человек увидел или прочитал уведомление. Смена аккаунта/привязки, отзыв исходной сессии или установки блокирует отправку, контент и квитанции. Записи тестов хранятся 24 часа; токены и тексты не выводятся в transport envelope или логи. Живую проверку запускает только явное действие владельца на телефоне.

Каждый монитор параметризованного списка содержит `notificationChannels` — массив включённых готовых каналов `telegram`, `max`, `email`, `webhook` (либо `[]`). Сервер учитывает флаги каналов, состояние адресата и подтверждение выбранного email уведомлений; адреса, чаты, webhook URL и секреты в эту сводку не входят. Значки показывают конфигурацию маршрутов, а фактическую доставку подтверждает отдельная приёмка.

`checkType` принимает `http`, `tcp` или `icmp`; отсутствие типа в старом POST означает HTTP, в PATCH сохраняет текущий тип. HTTP использует `url/method/expectedStatus/bodyContains`; TCP — `host/port` (1–65535), ICMP — `host`. Несовместимые поля отклоняются. При смене типа задаётся новая цель; переход на HTTP требует URL, метода и ожидаемого статуса. Смена типа, адреса или порта использует тот же сброс конфигурации, что изменение HTTP-условий: новая версия, отмена старой аренды, `config_changed` для открытого инцидента, новая проверка. Запоздавшие результаты не применяются к новой конфигурации.

Миграция `0015_monitor_check_types.sql` сохраняет старым мониторам и результатам тип HTTP. Результат возвращает собственный `checkType`, поэтому смена типа монитора не переименовывает старые измерения. `latencyMs` — общая длительность попытки, включая DNS и перебор адресов; это не ICMP-пинг. `roundTripMs` (и `lastRoundTripMs` у монитора) заполняется только для успешного ICMP: отправка запроса → совпавший ответ. При таймауте RTT отсутствует. Сводная статистика продолжает хранить длительность проверки, а не усреднённый пинг.

Настройки `intervalMinutes` и `failureThreshold` — целые числа от 1 до 10. POST без этих полей создает монитор с интервалом 5 минут и порогом 2; явные значения вне диапазона отклоняются с `400`. PATCH без полей сохраняет текущие настройки и по-прежнему требует `version`. GET и список всегда возвращают оба значения. Формы создания и редактирования позволяют выбрать их отдельно для каждого монитора.

Миграция `0004_monitor_scheduling.sql` сохраняет существующим мониторам интервал 1 минуту и порог 2; новые получают значения 5 и 2. Ранее примененные миграции не меняются. Изменение интервала или порога использует тот же атомарный путь, что смена URL/условий: новая версия, отмена текущей аренды, сброс серии ошибок и свежего состояния, закрытие открытого инцидента с `config_changed`, ближайшая проверка сразу после сохранения. Повторное сохранение тех же значений и переименование состояние не сбрасывают.

Настройки покрыты PostgreSQL-тестами с `-race`: обновление старой схемы, defaults и валидация API, расписание и свежесть для 1/5/10 минут, пороги 1/3/10, повторы результатов, UNKNOWN и изменение конфигурации с активной арендой. В Chrome проверены создание 5/2, редактирование 10/3 и 1/1, сохранение после reload, обе темы и мобильные формы 320/390 px. Реальные worker/probe получили HTTP200 и назначили следующую проверку через выбранные 5 и 10 минут. Это не нагрузочная приемка количества мониторов.

1. `worker` выбирает наступившие задания через `FOR UPDATE SKIP LOCKED` в короткой транзакции
2. Задание получает `run_id`, версию настроек `config_version`, срок аренды исполнения и токен текущей попытки
3. Транзакция завершается. `worker` вызывает `probe` по закрытому HTTP-интерфейсу с внутренней аутентификацией и ограничением времени
4. `probe` проверяет адрес, выполняет запрос и возвращает ограниченный результат
5. `monitors` принимает результат только для актуальной попытки и конфигурации. Результат и событие `CheckCompleted` записываются одной транзакцией
6. `incidents` последовательно обрабатывает результаты одного монитора. Изменение инцидента и событие для будущей доставки записываются одной транзакцией
7. На следующем этапе `notifications` будет создавать отдельные доставки по каналам. Отправка провайдеру должна происходить вне транзакции

Инцидент открывается при достижении выбранного `failureThreshold` последовательных DOWN: при пороге 1 — после первой ошибки, при 2 — после второй и так далее. Первая успешная проверка закрывает его с причиной `recovered`; для настроенного webhook создается доставка. UNKNOWN обнуляет серию ошибок, не закрывая уже открытый инцидент как восстановленный. Повторы обработки одного результата не считаются новыми проверками. Первый успешный запуск без предшествующего сбоя не создает событие о восстановлении.

Следующая проверка планируется от завершения текущей через `intervalMinutes`; такой же интервал используется при отложенной проверке без доступа. Отсутствие результата или его возраст более двух выбранных интервалов плюс 30 секунд дает состояние `UNKNOWN`: 150 секунд для 1 минуты, 630 для 5 и 1230 для 10. Это проверка свежести отображаемого состояния, она сама по себе не создает инцидент. Ошибка собственного worker или probe не доказывает падение сайта. Пауза и отсутствие доступного места в квоте имеют отдельные статусы, а не имитируют инцидент на стороне пользователя.

Аренда задания и токен попытки позволяют восстановиться после падения worker и отклонить запоздалый результат. Обработка событий сохраняет порядок внутри монитора, а повторное событие не меняет состояние второй раз. После простоя не выполняется залп всех пропущенных проверок. Параллелизм ограничен по системе, аккаунту и целевому адресу.

Выбранный интервал не является обещанием срока доставки уведомления. В задержку входят ожидание очередной проверки, таймаут, число сбоев для подтверждения и доставка. Перед коммерческим запуском отдельно проверяется влияние места размещения probe на ложные срабатывания.

### Изоляция probe

`probe` не подключается к PostgreSQL и не получает ключи ЮKassa, SMTP или ботов. Он принимает только данные конкретной проверки от worker по внутреннему интерфейсу с общим секретом и возвращает ограниченный результат. Локально интерфейс слушает loopback; публиковать его для пользователей нельзя.

Исполнитель защищается от SSRF: разрешенные схемы и порты, запрет внутренних и служебных IPv4/IPv6, проверка каждого DNS-результата и редиректа, соединение только с проверенным адресом. Повторное разрешение имени не должно позволять обойти проверку через DNS rebinding. Сетевые ограничения окружения дополняют проверки в коде.

HTTP ограничен публичными GET/HEAD по `http:80` и `https:443`, телом до 1 MiB и тремя перенаправлениями. TCP устанавливает соединение с одним портом 1–65535 и сразу закрывает его без передачи пользовательских данных. ICMP отправляет небольшой Echo Request с уникальным содержимым попытки и проверяет источник, тип, код, sequence и содержимое ответа. На попытку выделяется до 10 секунд; DNS и отдельное соединение/ожидание ответа ограничены тремя секундами, перебираются не более четырёх проверенных адресов.

Новые TCP/ICMP проверки поддерживают IPv4. Все DNS-ответы сначала проверяются на публичность, затем выбираются A-записи; имя только с AAAA даёт `UNKNOWN/address_family_unavailable`. Буквальный IPv6 в этих режимах отклоняется при настройке. Production probe работает в сети без IPv6. Для ICMP используется непривилегированный ping socket, разрешённый только GID 65532 через `net.ipv4.ping_group_range`; nonroot, `cap_drop: ALL` и `no-new-privileges` сохраняются. Ошибка собственных сетевых прав или ресурсов — UNKNOWN, а не падение сервера. Одновременно выполняются не более четырех проверок в целом, двух на аккаунт и одной на целевой адрес. Каждый DNS-результат и новый адрес перенаправления проходят повторную проверку; полное тело ответа в историю не сохраняется. Пользовательские заголовки и учетные данные проверяемого API пока не принимаются.

### Платежи и подписка

`billing` хранит административную квоту, независимые оплаченные пакеты мест, заказы и результаты оплаты. При регистрации общая квота равна нулю; `local_test` недействителен в production. Активные допустимые части складываются, каждая истекает в собственный срок. Общий `activeUntil` показывает ближайшее истечение текущей суммы, а `monitorCount` — все сохранённые мониторы; число включённых и реально работающих мест передаётся отдельно. Тестовый магазин ЮKassa доступен одному разрешённому аккаунту, отдельный production-магазин — всем активным аккаунтам после активации. Возвраты и автопродление пока не включены. Правила квоты и периода принадлежат Heartbeat Checker, платёжный статус подтверждает API провайдера.

1. Go рассчитывает сумму по серверному тарифу и сохраняет заказ с квотой и периодом
2. До запроса в ЮKassa сохраняются попытка платежа и ключ идемпотентности
3. Пользователь переходит на платёжную страницу ЮKassa по ссылке подтверждённого заказа
4. После webhook или фоновой сверки Go запрашивает платеж у ЮKassa и проверяет успешный статус, сумму, валюту, магазин и связь с локальным заказом
5. Подтверждённая оплата атомарно создаёт отдельный пакет или продлевает только выбранный пакет; остальные пакеты и административная часть остаются независимыми. Удалённый аккаунт не восстанавливается. Повторное уведомление не выдаёт доступ повторно

Миграция `0026_independent_packages` сохраняет все существующие подписочные, локальные и тестовые строки, их квоты, сроки, версии и причины. Для них `id=account_id`, `origin_order_id=NULL`; новые покупки получают отдельные строки с уникальной связью с заказом. Исторические заказы получают только классификацию `legacy` без изменения результата и без выдачи доступа. `packages` всегда содержит массив сохранённых пакетов с вычисленным `active`; старое поле `paid` остаётся совместимой проекцией и не используется для выбора покупки или продления. Новый checkout передаёт `purchaseKind` и `packageId` для продления; неоднозначный старый запрос получает `billing_selection_required`. После начала DDL применимо только восстановление вперёд с matching image: старый writer рассчитан на уникальный `account_id` и не должен запускаться против новой схемы.

Возврат браузера с платежной страницы не подтверждает оплату. При сетевой ошибке результат сначала сверяется с провайдером. Повтор одной операции использует исходный ключ. ЮKassa поддерживает его идемпотентность 24 часа, поэтому неизвестное списание после этого срока не повторяется автоматически. [Формат API](https://yookassa.ru/developers/using-api/interaction-format), [webhooks](https://yookassa.ru/developers/using-api/webhooks)

В будущем добровольное автопродление потребует сохранённого согласия пользователя и подтверждённого сохранения способа оплаты. Для платежа продления потребуется уникальная связь с подпиской и расчётным периодом, а перед новым списанием — проверка отказа от автопродления. Реализация отложена; перед её запуском нужно отдельно проверить подключение автоплатежей к реальному магазину. [Автоплатежи ЮKassa](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/recurring-payments/basics)

Каждая новая покупка создаёт независимый пакет мест. Оплаченный период пакета — календарный месяц от даты и времени подтверждённого применения заказа до соответствующего момента следующего месяца; при отсутствии такого числа используется последний день месяца, исходное число сохраняется для последующих продлений. При явном продлении выбранного активного пакета следующий месяц начинается после его текущего срока; для истёкшего пакета начинается новый полный месяц с момента применения оплаты. До оплаты показаны число мест, сумма и правила периода; точные даты отображаются после применения заказа, время для пользователя — московское.

Выбранный пакет продлевается в том же размере; отдельный новый пакет можно купить в любой день, даже при действующих пакетах. Их активные места складываются, сроки остаются отдельными. Клиент явно выбирает новую покупку либо пакет для продления; неоднозначный старый запрос требует повторного выбора. Создание и включение мониторов проверяют число включённых конкурентно, чтобы два одновременных запроса не превысили лимит. Пауза освобождает место для другого сохранённого монитора, не отменяет оплаченный период и сохраняет настройки и историю. Если после истечения одной из частей квоты включённых мониторов стало больше доступных мест, проверки сверх лимита получают `SUBSCRIPTION_REQUIRED` до освобождения места или восстановления квоты.

После окончания оплаченного периода worker продолжает проверки только в пределах оставшейся действующей квоты. Поздний результат не снимает ограничение по местам. Доступ к кабинету, оплате и истории в пределах срока хранения сохраняется. Правила возвратов и параметры чеков оформляются до реальных платежей с учетом настроек продавца.

Владелец работает как ИП на НПД и выбрал ручное формирование чеков в «Мой налог» с передачей покупателю. Автоматизация чеков не является условием старта; до продаж нужен учет выданных чеков и сверка с платежами/возвратами. «Чеки от ЮKassa» по 54-ФЗ не подменяют этот порядок: [инструкция провайдера исключает НПД](https://yookassa.ru/docs/support/merchant/payments/implement/docs). Реквизиты ИП опубликованы отдельно от исходных личных документов.

### Доставка уведомлений

Реализован один исходящий webhook на монитор. После подтвержденного DOWN или восстановления UP API в той же транзакции сохраняет событие и доставку. Работает только HTTPS на порту 443; probe повторно проверяет DNS и конечный адрес перед POST. Настройки доступны авторизованному владельцу монитора независимо от оплаченной квоты:

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/v1/monitors/{id}/webhook` | Получить адрес, состояние и версию; секрет не возвращается |
| `PUT` | `/api/v1/monitors/{id}/webhook` | Создать или изменить `{ "version": 0, "url": "https://example.com/hook", "enabled": false, "rotateSecret": false }`; при изменении указать текущую версию и `id` endpoint |
| `DELETE` | `/api/v1/monitors/{id}/webhook` | Удалить endpoint и его историю доставок; обязательное JSON-тело `{ "id": "<endpoint UUID>", "version": 1 }` |
| `GET` | `/api/v1/monitors/{id}/webhook/deliveries?limit=50&before=...` | Получить историю, не более 100 записей; `before` — RFC3339Nano |

В кабинете webhook находится в уведомлениях монитора, независимо от Email/Telegram/MAX. Новый адрес создаётся выключенным: сначала сохраните одноразовый секрет у получателя, затем явно включите доставку. Смена URL и ротация требуют подтверждения и сохраняют webhook выключенным; после настройки получателя его нужно включить снова. При неизвестном результате записи интерфейс сверяет текущее состояние GET-запросом и не повторяет PUT автоматически. В истории показаны последние 50 доставок без подгрузки старых записей.

`PUT` возвращает `webhook` с новой версией и `secret` только при создании, изменении адреса или `rotateSecret: true`. Сохраните секрет при получении: API хранит его зашифрованным и позже не показывает. Смена адреса, отключение и ротация отменяют незавершенные доставки прежней версии; уже отправляемый POST может завершиться у получателя после изменения настройки. Worker сохраняет занятый слот до ответа или истечения lease и отклоняет устаревшее завершение в БД. Повторное включение не воспроизводит старые события. При несовпадении версии или переданного ID endpoint API отвечает `409`, при чужом мониторе или отсутствующем endpoint — `404`. DELETE без JSON-тела больше не поддерживается: требуется актуальная пара `id` и `version`, чтобы устаревшая вкладка не удалила пересозданный endpoint с новой историей. Создание использует `version: 0` без `id`; PUT с `id` не создаёт отсутствующий endpoint. Для изменений действуют обычные origin/CSRF проверки авторизации.

Тело POST — JSON с полями `schemaVersion: 1`, `id` (UUID события), `type` (`monitor.down` или `monitor.up`), `occurredAt`, `monitorId`, `incidentId`, `sequence`. В заголовках передаются `X-Heartbeat-Event-Id`, `X-Heartbeat-Timestamp` (Unix seconds) и `X-Heartbeat-Signature: v1=<hex>`. Подпись — HMAC-SHA256 по байтам `timestamp + "." + eventId + "." + exactBody`; ключ HMAC — 32 байта, полученные base64url-декодированием выданного `secret`. Получатель должен проверять подпись постоянным по времени сравнением, ограничивать возраст timestamp (например, пятью минутами) и запоминать `id` для подавления дублей. Timestamp и подпись обновляются при каждой попытке, тело и id остаются теми же.

Пример проверки подписи на Go (читайте исходные bytes тела до JSON-декодирования):

```go
func validWebhook(secret, timestamp, eventID, signature string, body []byte) bool {
    key, err := base64.RawURLEncoding.DecodeString(secret)
    if err != nil || len(key) != 32 || !strings.HasPrefix(signature, "v1=") { return false }
    sentAt, err := strconv.ParseInt(timestamp, 10, 64)
    if err != nil || math.Abs(time.Since(time.Unix(sentAt, 0)).Seconds()) > 300 { return false }
    supplied, err := hex.DecodeString(strings.TrimPrefix(signature, "v1="))
    if err != nil { return false }
    mac := hmac.New(sha256.New, key)
    mac.Write([]byte(timestamp + "." + eventID + "."))
    mac.Write(body)
    return hmac.Equal(supplied, mac.Sum(nil))
}
```

После проверки сравните `eventID` с `id` внутри JSON и сохраните `eventID` с уникальным ограничением в своей БД до выполнения действия. Повтор с тем же ID подтверждайте без повторного действия.

Worker отправляет до восьми попыток за 24 часа с задержками 30 секунд, 2, 10, 30 минут, 2, 6 и 12 часов. Повторяются сетевые ошибки, таймауты, HTTP 408, 429 и 5xx; другие ответы завершают доставку. DOWN и UP идут по порядку в пределах endpoint; окончательная ошибка открывает очередь следующему событию. История конечных статусов хранится 30 дней. Возможны повторы после потери ответа, поэтому получатель должен обрабатывать `id` идемпотентно. Успешный HTTP 2xx означает прием endpoint, а не исполнение действия на его стороне.

Привязки получателей создаются через сайт с подтверждением владения каналом. Бот Telegram нужен для технической доставки и привязки, отдельное управление сервисом в боте не разрабатывается.

Для Telegram клиент выбирает получателя: личный чат с ботом, группу/супергруппу или конкретный топик группы с включенными темами. Получатели привязываются в кабинете и затем выбираются в настройках монитора. Для группы без выбранного топика отправка идет в общий чат; для выбранного топика сохраняется отдельный `message_thread_id` вместе с `chat_id`. Разные топики одной группы являются разными получателями. Это требование пользователя от 18.10.2026 к будущему модулю доставки, а не уже работающая отправка.

Привязка выполняется одноразовым ограниченным по времени кодом из кабинета и подтверждается действием пользователя в нужном чате/топике. Для группы проверяются права связывающего пользователя и право бота отправлять сообщения; одного введенного ID недостаточно. В кабинете отображаются название чата, выбранный топик и состояние связи. Удаление бота, запрет отправки, удаленный или закрытый топик дают видимую ошибку доставки; автоматического переноса сообщения из выбранного топика в общий чат нет. Миграция группы в супергруппу должна сохранять связь с учетом нового `chat_id`. При удалении получателя прекращаются новые доставки этому адресу. [Telegram: sendMessage](https://core.telegram.org/bots/api#sendmessage), [привязка через deep link](https://core.telegram.org/bots/features#deep-linking)

Каждая доставка хранит канал, получателя, событие, статус и попытки. Для Telegram, email и MAX используются отдельные адаптеры и ограничения скорости. Повторы учитывают ответы провайдера, включая `retry_after`, имеют ограничение попыток и видимую причину окончательной ошибки.

События сбоя и восстановления обрабатываются последовательно для конкретного монитора и получателя. Ошибка одного канала не останавливает остальные. Успешный ответ API провайдера означает прием сообщения провайдером, а не прочтение пользователем. При потере ответа после успешной отправки возможен дубль, гарантии `exactly once` нет.

### Локальная разработка и порядок реализации

Локальное окружение уже включает Go API, worker, probe, Next.js, PostgreSQL и Mailpit; команды запуска приведены выше. Тестовый checkout и уведомления мониторинга через Telegram/MAX и email реализованы; каналы выключены по умолчанию и требуют явной настройки. Production-магазин ЮKassa включён отдельно от тестового; состояние конкретных заказов и внешней приёмки фиксируется в `../context.md`. Production-очередь служебных писем auth подготовлена отдельно. Исходящие webhook и email требуют отдельной сквозной проверки с разрешенным тестовым получателем; наличие кода и зеленая сборка сами по себе не подтверждают внешнюю доставку. Сетевой тест Turnstile использует официальные тестовые ключи и требует доступа к Cloudflare. Это не полностью автономный режим без интернета.

Тестовые упрощения включаются только явной локальной конфигурацией. Они не дают скрытого обхода авторизации, оплаченных лимитов или защиты URL. Секреты находятся в локальных игнорируемых файлах. Пример конфигурации содержит только названия параметров и безопасные значения.

Реализованы каркас Go, конфигурация, PostgreSQL и миграции, auth с Turnstile, сессиями и профилем, независимые части квоты, мониторы, планировщик, probe, результаты, инциденты, очистка истории и истекших auth-данных, лендинг и основной кабинет. Подробные результаты сохраняются 7 дней; закрытые инциденты, дневная статистика и обработанные события outbox — 90 дней. Worker удаляет просроченные данные ограниченными порциями. Для backend-деплоя и production-очереди служебных писем предусмотрены отдельные проверки и запись фактического результата в `../context.md`; техническая готовность не означает сквозную приёмку через реальный аккаунт и провайдеров. Сквозную приёмку Telegram/MAX Informer и email-уведомлений владельцем фиксируют отдельно; административный интерфейс реализован с отдельной MFA-проверкой.

При проверке ключевыми являются изоляция аккаунтов, SSRF, истечение сессий, повторные webhooks, конкурентное изменение квоты, перезапуск worker и ошибки внешних провайдеров. Готовность к реальному запуску требует отдельной проверки магазина ЮKassa, почты, ботов, резервного копирования и восстановления.

### Android APK и запуск кабинета

Версия Android 2.3.2 (`versionCode 14`) в исходниках `apps/android` — React Native-приложение с полноценной нативной публичной страницей сервиса, помощью, экранами входа, регистрации, мониторов, уведомлений, оплаты и аккаунта. Пакет `ru.heartbeatchecker.app` и прежний сертификат подписи сохраняются для обновления установленного APK 1.2.0. Сайт остаётся отдельным веб-клиентом. Встроенный WebView показывает только Cloudflare Turnstile без полей авторизации; внешние OAuth-страницы открываются в Custom Tab, а короткий callback-код обменивает приложение. Android App Links для сброса пароля, подтверждения регистрации, платежей и инцидентов проходят строгую проверку origin/path/параметров и повторную проверку прав на сервере. Native-сессии не используют браузерные cookies.

Новая покупка использует встроенную форму YooKassa только при совпадении серверной capability и публичной конфигурации APK; иначе остаётся hosted-оплата. Сохранённое платёжное намерение закрепляет адаптер и idempotency key до POST. После перезапуска приложение сначала запрашивает статус заказа, а успешной считает лишь оплату с серверным начислением. Публичный сайт продолжает hosted-сценарий. Для проверки test-магазина есть отдельный `sdkTest` APK с суффиксом `.sdktest` и локальным API через `adb reverse`; это не переключает production-магазин.

`/android` показывает проверенные версию, дату, размер и SHA-256 текущего публичного APK. `/apps/android/download` отдаёт его потоково с того же домена по неизменяемому URL из проверенного release manifest; старый `/downloads/android` перенаправляет только на этот относительный путь (307). GET и HEAD проверяют ответ 200, MIME APK, размер менее 100 МиБ, допустимый Content-Encoding и точный SHA-256 перед завершением выдачи. Ошибка upstream обрывает файл; frontend не обращается к S3 при сборке, запуске или readiness. `apps/web/src/shared/android/release.json` остаётся на опубликованной версии 1.2.0 до отдельного продвижения принятого нового APK. Digital Asset Links формируются из этого публичного manifest; запись кандидата в него до приёмки недопустима.

Workflow `Build or publish Android` по умолчанию только собирает подписанного кандидата из полного SHA в master после успешного exact-SHA CI. `android-release` получает защищённый keystore, а проверенный APK и release manifest сохраняются как неизменяемые GitHub artifacts. Отдельный запуск с явным `publish=true` и `candidate_run_id` скачивает именно принятый artifact, повторно проверяет SHA, ancestry, CI, подпись и checksum и только затем выполняет публикацию через защищённый `production-backend` job. Зашифрованный signing recovery архив и scoped SSH используются только в режиме публикации: резервная копия сохраняется приватно, S3 APK записывается условно без перезаписи, receipt и публичный SHA-256 проверяются. Секреты S3 и raw keystore не входят в APK или frontend. После публикации отдельный metadata-коммит обновляет публичный release manifest сайта.

Обычный CI проверяет TypeScript, Android lint/unit tests, offline-bundled `assembleCi` и instrumentation smoke на эмуляторе API 35. Эти проверки не заменяют обновление старого подписанного APK, сценарии OAuth/платежа/push на физических устройствах и ручную приёмку владельцем. Публикация APK на сайте и модерация RuStore остаются отдельными действиями; этот workflow не отправляет сборку на модерацию. Подробности сборки и устройства — в `apps/android/README.md`.

Отдельный workflow `Build or publish Android Dev` собирает `ru.heartbeatchecker.app.dev` с собственной подписью и Metro по Wi-Fi. Его APK и манифест сохраняются как GitHub artifact точного source SHA. При явной публикации проверенные package, подпись, размер и SHA-256 помещаются в `/opt/heartbeat-checker/backend/android-dev-private/payload` на существующем backend VPS; API получает только read-only mount. `GET/HEAD /api/v1/admin/android-dev` и `/api/v1/admin/android-dev/apk` требуют веб-сессию admin с действующей MFA. В веб-админке `/app/admin` карточка «Разработка Android» изначально отсутствует и появляется только после подтверждения MFA и успешного ответа закрытого metadata endpoint; загрузка вновь проверяет права для GET, HEAD и Range. Браузер сохраняет dev APK под именем `devHeartbeat Checker.apk`; внутреннее имя файла остаётся `Heartbeat-Checker-dev.apk`. На публичной странице `/android` dev-кнопки нет. Публичный APK, его манифест и RuStore этим workflow не меняются.

### Индексация публичного сайта

SEO-настройки разрешают индексацию только `/`, `/android`, `/contacts`, `/terms`, `/privacy` и `/cookies`. У страниц отдельные title/description, production canonical, Open Graph/Twitter и компактный JSON-LD по содержимому. Корневой metadata и HTTP-заголовок по умолчанию сохраняют `noindex, nofollow`; авторизация и кабинет остаются доступными для обхода, чтобы поисковый робот мог прочитать этот запрет. Sitemap содержит ровно шесть публичных URL без выдуманной даты изменения. Robots исключает технические API/downloads/assetlinks-пути; это не механизм авторизации.

Карточка `/og` — статический PNG 1200×630, сформированный при сборке из исходного знака сервиса и локального OFL-шрифта. Готовый `apps/web/public/fonts/golos-text-og.ttf` хранится в Git; `go -C tools run ./cmd/hc-ops font-check` проверяет его точный SHA256, контрольные суммы исходных Golos Text Latin/Cyrillic WOFF2 и OFL-лицензии, а также наличие латинских и кириллических глифов. Проверка не конвертирует и не генерирует шрифт. Если понадобится новый TTF, его подготовка выполняется отдельно согласованным внешним инструментом; после проверки лицензии, происхождения и отображения обеих письменностей обновляются артефакт и ожидаемые контрольные суммы. Внешние изображения, шрифты и аналитика не подключаются. Разметка Android SoftwareApplication появляется только при проверенном ненулевом Android release manifest.

После `npm run build` и локального запуска приложения проверка фактического HTML: `go -C tools run ./cmd/hc-ops seo-smoke --base-url http://127.0.0.1:3139`. Она проверяет публичные metadata/canonical, PNG, JSON-LD, private noindex, robots, sitemap и настоящий 404. Для сайта за Caddy добавьте `--require-api-header`: frontend Caddy ставит отложенный `X-Robots-Tag: noindex, nofollow` на `/api/v1/*`, включая прямые OAuth callbacks. Локальный Next rewrite может не сохранять response headers API, поэтому локальный smoke проверяет API отдельно от HTML; production/edge проверяется строго. Эта проверка не измеряет Core Web Vitals и не подтверждает индексацию или позиции в поиске.
