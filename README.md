# Heartbeat-Checker_monorepo

## Архитектура:

Heartbeat Checker - коммерческий сервис проверки доступности сайтов и API. Пользователь управляет мониторингом через сайт и получает уведомления о падении и восстановлении.

Домен проекта — `heartbeat-checker.ru`, будущий публичный origin — `https://heartbeat-checker.ru`. Сейчас приложение запускается только локально; домен не меняет локальные адреса и тестовые ключи.

Документ разделяет работающую локальную реализацию и целевые продуктовые требования. Состояние исходников актуализировано 18.10.2026. Платежи, уведомления и административный интерфейс остаются следующими этапами.

### Текущее состояние и запуск

Работают Go API авторизации, профиля, квоты и мониторов, отдельные `worker` и `probe`, Next.js лендинг и кабинет. API использует PostgreSQL, структурированные логи и корректное завершение. `/healthz` проверяет HTTP-сервер, `/readyz` выполняет Ping БД с таймаутом; при недоступной БД readiness возвращает 503, после восстановления — 200.

Требуются Go 1.27+, Node.js 24.21+, Docker с Compose и `make`. PostgreSQL 18.6 запускается на `127.0.0.1:55432`, Mailpit принимает локальную почту на `127.0.0.1:51025`, его UI доступен на `http://127.0.0.1:58025`. Данные БД сохраняются в volume локального Compose-проекта.

Из корня монорепозитория:

```sh
make local-up   # PostgreSQL и локальный SMTP-приемник Mailpit
make init-local # Создать игнорируемый секрет связи worker и probe
make migrate    # Применить SQL-миграции отдельной командой
```

В отдельных терминалах запустите процессы:

```sh
make run     # Go API на 127.0.0.1:8080
make probe   # Изолированный HTTP-исполнитель на 127.0.0.1:8090
make worker  # Планировщик проверок и очистка данных
```

Для сайта установите зависимости из lockfile и запустите Next.js на `http://127.0.0.1:3000`:

```sh
cd apps/web
cp .env.example .env.local
npm ci
cd ../..
make web-dev
```

В `.env.local` адрес `GO_API_ORIGIN=http://127.0.0.1:8080` нужен серверному proxy Next.js; браузер обращается к API через origin сайта `http://127.0.0.1:3000`. Для локального запуска production-сборки frontend используйте из `apps/web` команды `npm run build` и `npm start` с той же конфигурацией. Это локальный режим сборки, а не развертывание публичного сайта.

Проверки и служебные команды:

```sh
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
make check             # gofmt, go vet, Go-тесты и сборка backend
make test-integration  # HTTP/SQL-сценарии в отдельных временных БД
make test-smtp-auth    # PostgreSQL и Mailpit, заглушка капчи
make test-live-auth    # Реальные Siteverify и Mailpit; нужна внешняя сеть
```

`make db-up` запускает только PostgreSQL, `make mail-up` — только Mailpit. `make db-down` останавливает контейнеры локального Compose-проекта, сохраняя volume БД. Почта Mailpit временная и не сохраняется после удаления контейнера. Тестовые учетные данные предназначены только для локального окружения.

`make run` задает локальные значения `DATABASE_URL`, `AUTH_ORIGIN=http://127.0.0.1:3000`, cookie, Turnstile и SMTP; экспортированные переменные их переопределяют. `make worker` и `make probe` используют общий секрет из `.local/probe-secret`, который создает `make init-local`. При прямом запуске Go обязательны переменные соответствующего процесса из `.env.example`; неполная конфигурация останавливает запуск. API не применяет миграции автоматически. `make migrate` блокирует конкурентное применение, записывает контрольные суммы и отклоняет изменение уже примененного SQL.

`.env.example` описывает параметры и не загружается автоматически; приложения читают environment. Таймауты API по умолчанию: соединение с БД 5 секунд, readiness 2 секунды, завершение 10 секунд.

Новый аккаунт получает квоту 0: регистрация сама по себе не разрешает создать монитор. Только для локальной разработки выдайте квоту явно, взяв `account.id` из `GET /api/v1/me` после входа:

```sh
make grant ACCOUNT_ID=ваш-uuid LIMIT=2 UNTIL=2026-11-18T00:00:00Z
```

Команда работает только при `APP_ENV=local` и подключении к проектной loopback-БД; источник `local_test` в production не считается действительным правом. Монитор создается и включается только в пределах действующей квоты. Платежей и выдачи оплаченной квоты пока нет.

Для первоначального локального администратора есть отдельная create-only команда. Она в одной транзакции создает активный профиль с ролью `admin`, учетные данные и тестовую квоту. Существующий email, в том числе при конкурентном запуске, приводит к отказу без изменения профиля, пароля, сессий и квоты. Обычная регистрация всегда создает роль `user`.

Создайте файл `.local/admin-password` локально через редактор или скрытый ввод, без пароля в командах, аргументах или environment. Файл должен быть обычным, с правами `0600`, и содержать ровно пароль длиной 12–1024 байта. Пробелы и переводы строк сохраняются как часть пароля: не добавляйте завершающий перевод строки. Symlink и другие типы файлов отклоняются. `.local/` исключен из Git.

```sh
chmod 600 .local/admin-password
ADMIN_EMAIL=owner@example.test \
ADMIN_NAME='Local owner' \
ADMIN_QUOTA=10 \
ADMIN_UNTIL=2027-10-18T00:00:00Z \
ADMIN_PASSWORD_FILE=../.local/admin-password \
ADMIN_REASON='Explicit local owner bootstrap' \
make local-admin
```

`ADMIN_PASSWORD_FILE` в этой Make-команде задается относительно `backend/`; остальные параметры также обязательны и выбираются явно. Для прямого запуска: `cd backend`, затем `APP_ENV=local bin/local-admin --email … --name … --quota … --until … --password-file … --reason …`. Команда сначала проверяет `APP_ENV=local` и точный адрес проектной loopback-БД, а уже затем читает пароль и подключается к PostgreSQL. Hash Argon2id вычисляется до транзакции. Команда не отправляет письмо, не создает сессию и не выдает оплаченный доступ; тестовая квота имеет источник `local_test` и выбранный срок.

Администратор входит через обычную форму с Turnstile и использует собственный кабинет мониторинга. Административные HTTP-операции и административный интерфейс остаются закрыты до реализации MFA; эта команда их не открывает. Локальный CLI собирается в `make check` и CI, но не включается в production-образы. После успешного запуска удалите файл с паролем, когда он больше не нужен.

Для auth/accounts прошли `make check`, `go mod verify`, тесты с `-race` и реальной PostgreSQL, повторное применение миграций, SMTP smoke и `make test-live-auth`. Живой сценарий проверил Siteverify с официальными тестовыми ключами, регистрацию, письмо, подтверждение, вход, сброс пароля, отзыв старой сессии и повторный вход; временные БД и письма тестов удалены. Сквозная HTTP-проверка через Next.js proxy подтвердила регистрацию, подтверждение, вход, отказ без квоты (`403`), отказ при исчерпании квоты (`403`) и CSRF (`403`). Отдельные worker/probe получили реальный UP/HTTP 200 от example.com; два несовпадения ожидаемого кода открыли один инцидент. Пауза сохраняет занятое место в квоте.

В Chrome проверены кабинет авторизованного тестового аккаунта, история результатов/инцидентов, редактирование условия и завершение инцидента с причиной «Настройки изменены», отображение профиля и двух сессий. Полная браузерная проверка регистрации, изменения профиля, отзыва сессий и мобильной верстки пока не завершена: управление периодически блокируется UI другого расширения. Эти сценарии нельзя считать принятыми только по API-тестам.

GitHub CI проверяет Go и frontend, интеграционные сценарии, конфигурацию доставки и откат, затем собирает образы API, worker, probe, migrate и web. Отдельный workflow `Deploy frontend` готовит публичный web-образ и доставляет его на предоставленный frontend VPS. Публичное приложение пока не запущено: сервер backend еще не предоставлен, `GO_API_ORIGIN` не задан.

### Подготовка frontend VPS и доставка

Frontend размещается отдельно от Go и PostgreSQL. Скрипт `deploy/frontend/bootstrap.sh` предназначен для чистой Ubuntu 22.04/24.04/26.04 amd64: устанавливает Docker Engine и Compose из официального подписанного репозитория, создает пользователя `heartbeat-deploy` и каталог `/opt/heartbeat-checker/frontend`. Один публичный SSH-ключ передается через stdin:

```sh
sudo bash bootstrap.sh < /path/to/frontend-deploy-key.pub
```

До подключения сверяется SSH host key сервера. Bootstrap сохраняет существующий root/парольный доступ и настройки firewall; ключ CI запрещает PTY и forwarding. Пользователь входит в группу Docker и поэтому имеет административные возможности на этом выделенном VPS. Приватный ключ не включается в исходники.

В GitHub Actions нужны следующие repository variables и secrets:

| Тип | Имя | Назначение |
| --- | --- | --- |
| Variable | `WEB_PUBLIC_ORIGIN` | `https://heartbeat-checker.ru` |
| Variable | `GO_API_ORIGIN` | Реальный HTTPS origin отдельного Go API; не адрес frontend |
| Variable | `TURNSTILE_SITE_KEY` | Настоящий публичный site key для домена |
| Variable | `FRONTEND_DEPLOY_HOST` | IP или имя frontend VPS |
| Variable | `FRONTEND_DEPLOY_USER` | `heartbeat-deploy` |
| Secret | `FRONTEND_DEPLOY_SSH_KEY` | Отдельный приватный ключ CI |
| Secret | `FRONTEND_DEPLOY_KNOWN_HOSTS` | Проверенные SSH host keys сервера |

Секрет Turnstile нужен только Go и не передается frontend или его сборке. Без настоящего API origin workflow останавливается до публикации. Не задавайте временный чужой IP или origin сайта вместо backend.

`Deploy frontend` запускается вручную из `master` с полным `source_sha`. Он проверяет присутствие коммита в истории master и успешный push-CI именно этого SHA, собирает web с production-параметрами, публикует в GHCR и передает immutable digest на VPS. Краткоживущий registry token передается через stdin; временные Docker credentials удаляются. Образ проверяется по OCI revision до переключения. Параллельные релизы сериализованы.

Compose запускает web в закрытой сети без host-порта 3000 и Caddy с автоматическим HTTPS. Для Caddy нужны доступные 80/443 TCP и 443 UDP; сертификаты сохраняются в Docker volume. API/auth не кэшируются. До переключения проверяется ответ Go `/api/v1/me` — `401` с `unauthorized`. После запуска проверяются HTTPS, главная, `/theme-init.js` и same-origin `/api/v1/me`. Неуспех восстанавливает предыдущие image/config; при неудаче первого запуска контейнеры останавливаются без удаления volumes. При ошибке самого отката файлы остаются для восстановления. Предыдущая успешная конфигурация сохраняется в `previous/`.

Bootstrap и конфигурация проверены, сценарии переключения/отката покрыты изолированными тестами. Реальный первый deploy и HTTPS postflight будут проверены после подготовки backend. Это доставка frontend, а не готовность коммерческого сервиса: реальная почта, trusted proxy IP, платежи и уведомления остаются отдельными задачами.

На этой машине LuLu задерживал первое внешнее соединение каждого нового временного Go-бинарника. После временного отключения LuLu пользователем полный live smoke прошел. При повторении таймаута нужно проверить разрешение конкретного Go-процесса в локальном сетевом фильтре; таймаут Siteverify и проверка TLS в коде не ослаблялись.

### Принятые решения

- Весь backend, включая уже работающие регистрацию, вход, сессии, проверки и права, пишется на Go; платежи запланированы здесь же
- Frontend - Next.js с архитектурой Feature-Sliced Design (FSD). Лендинг и личный кабинет реализованы; административный интерфейс запланирован с общими компонентами
- Пользовательские сценарии входа, кабинета и управления пользователями берем за образец из aeroCRM и адаптируем под мониторинг
- Better Auth и Keycloak в стартовую архитектуру не входят
- Капча - Cloudflare Turnstile. Токен проверяет Go-backend
- Вход и регистрация через Яндекс и VK запланированы на будущий этап; сейчас доступны email и пароль
- Настройки и управление находятся на сайте. Telegram и MAX используются для уведомлений и привязки получателя
- Каналы уведомлений - Telegram, email и MAX
- Android-приложение (APK) запланировано отдельным будущим этапом; способ реализации, распространения и мобильные push пока не выбраны
- Цена - 24 ₽ за монитор в месяц. Пользователь оплачивает квоту из N мониторов и может заменять URL внутри нее
- Оплата через ЮKassa. Доступны ручное продление и добровольное автопродление
- Пробного периода нет. Проверки запускаются в пределах оплаченной квоты
- Докупка квоты оплачивается пропорционально остатку периода. Уменьшение применяется со следующего периода
- Отмена автопродления сохраняет доступ до конца оплаченного срока. После окончания оплаты проверки приостанавливаются, кабинет и сохраненная история остаются доступны
- Для каждого монитора пользователь задает интервал 1–10 минут (для новых по умолчанию 5) и порог 1–10 последовательных неудачных проверок (по умолчанию 2). Первая успешная проверка закрывает инцидент
- Подробные результаты хранятся 7 дней. Инциденты и сводная статистика - 90 дней
- Сейчас разработка и проверка выполняются локально. Деплой будет отдельным этапом

### Основной подход

Модульный монолит на Go: одна кодовая база и один `go.mod`, разделенные на бизнес-модули с явными границами. Модули вызывают публичные контракты друг друга или обмениваются сохраняемыми событиями. HTTP между бизнес-модулями внутри процесса не нужен.

Из одной кодовой базы собираются три работающих процесса: `api` обслуживает сайт, `worker` планирует проверки и очищает данные, `probe` обращается к проверяемым URL. Такое разделение позволяет ограничить доступ исполнителя HTTP-проверок и отдельно управлять его нагрузкой.

| Компонент | Ответственность |
| --- | --- |
| Next.js | Страницы, формы, отображение данных и серверный рендеринг интерфейса |
| Reverse proxy | Единый origin для сайта и API. В дальнейшем HTTPS и внешняя маршрутизация |
| `api` | HTTP API, аутентификация, права и пользовательские операции; webhooks провайдеров запланированы |
| `worker` | Планирование проверок, обработка результатов и инцидентов, очистка истории; доставки и продления запланированы |
| `probe` | Ограниченное выполнение запросов к пользовательским адресам |
| PostgreSQL | Данные приложения, сессии, задания, результаты, события и учет доставок |

Для старта используется PostgreSQL без Redis и отдельного брокера сообщений. Сохраняемые задания и transactional outbox обеспечивают восстановление фоновой работы после перезапуска. Outbox - запись события в той же транзакции, что и изменение бизнес-данных; отправка уведомлений из него остается следующим этапом.

Отдельный API Gateway не нужен. Маршрутизация остается в reverse proxy, а проверка сессий и прав - в Go. Выделение новых сервисов или брокера рассматривается при измеримой потребности в независимом масштабировании, изоляции или пропускной способности.

Для деплоя пользователь выбрал размещение frontend на отдельном сервере. Next.js и публичный reverse proxy обслуживают `heartbeat-checker.ru`, а `/api/v1` проксируется к Go API на backend-сервере с worker, probe и PostgreSQL. Браузер продолжает использовать один origin; правила cookie, Origin и CSRF остаются в Go. До запуска нужны защищенное межсерверное соединение, ограничение доступа к API со стороны frontend, доверенная передача IP клиента и сетевое ограничение probe. Frontend VPS подготовлен; backend VPS и полноценное окружение еще отсутствуют.

Публичные `AUTH_ORIGIN` и `WEB_PUBLIC_ORIGIN` должны совпадать с `https://heartbeat-checker.ru`. Proxy передает `Origin`, `Cookie`, `Set-Cookie` и `X-CSRF-Token`, не кэшируя API/auth. Межсерверный канал — HTTPS с проверкой сертификата либо закрытый шифрованный туннель; PostgreSQL и probe не публикуются. Текущий `GO_API_ORIGIN` закрепляется в rewrites при сборке Next.js, поэтому смена upstream требует пересборки frontend. Поддержка доверенного IP клиента остается обязательной задачей до публичного запуска.

Тариф 24 ₽ обозначен как планируемый, а платежи и будущие уведомления явно отделены от работающего кабинета. В первом экране показана ускоренная демонстрация с условными данными и явно выбранными настройками примера: 5 минут и 2 сбоя. Содержательный текст и FAQ рендерятся сервером; интерактивная демонстрация находится внутри слайса `_pages/home` и не обращается к API.

Маршруты Next.js находятся в `apps/web/app`, а FSD-код - в `apps/web/src`. Слои App и Pages называются `_app` и `_pages`, чтобы не конфликтовать с особыми каталогами Next.js. Файл маршрута подключает готовую страницу, сам интерфейс находится в соответствующем слайсе. [FSD и Next.js](https://feature-sliced.design/docs/guides/tech/with-nextjs)

Порядок зависимостей: `_app > _pages > widgets > features > entities > shared`. Код импортирует нижние слои. Слайсы одного слоя изолированы, например `features/create-monitor` не импортирует `features/delete-monitor`. Их взаимодействие собирается на уровне страницы или виджета. [Слои FSD](https://feature-sliced.design/docs/reference/layers)

- Слайс называется по своему назначению. Например, `features/create-monitor` или `entities/incident`
- Внутри слайса используются нужные сегменты: `ui`, `model`, `api`, `lib`. Пустые сегменты не создаются
- Между слайсами используются явные публичные экспорты `index.ts`. Импорт внутренних файлов чужого слайса не допускается
- `shared/ui` не знает о мониторах и подписках. `shared/api` содержит общий транспорт, а запросы конкретной сущности находятся в ее слайсе
- Server-only код имеет отдельный публичный вход, если слайс используется и серверными, и клиентскими компонентами. Он не попадает в клиентский bundle
- Next.js отвечает за интерфейс и его рендеринг. Авторизация, платежные решения, права и бизнес-правила выполняются Go API
- Границы слоев и слайсов проверяются frontend-линтером. Реализованы лендинг, формы auth, кабинет, список и управление мониторами; billing и admin остаются следующими слайсами

### Правила модулей и читаемости кода

- `domain` не импортирует SQL, HTTP, провайдеров или соседние модули
- `service` описывает сценарий. Интерфейс зависимости определяется там, где он нужен, без интерфейса на каждый тип
- HTTP-обработчик проверяет формат запроса, вызывает сценарий и формирует ответ. SQL и бизнес-правила в обработчик не помещаются
- Репозиторий отвечает за хранение. Решения о тарифе, доступности сайта и правах остаются в прикладных сценариях и домене
- Каждый модуль владеет своими таблицами. Чтение и изменение чужих таблиц через собственный SQL не допускаются
- Для вызовов другого модуля используются `contracts`. Закрытые доменные типы и репозитории наружу не выдаются
- `module.go` собирает реализацию и предоставляет контракты и HTTP-обработчики. Только `app` связывает модули между собой
- Вложенный `internal` запрещает импорт реализации соседним модулем и пакетом `app`. `app` получает доступ через `module.go`
- `contracts` не зависит от собственного закрытого `internal`. Циклических импортов и обратной зависимости `platform` от модулей нет
- Зависимости передаются обычными конструкторами. Глобальные сервисы, скрытый service locator и DI-фреймворк не нужны
- `platform` содержит технические механизмы без бизнес-правил. Общий `pkg` и универсальные `helpers` заранее не создаются
- Функции имеют понятные имена и одну задачу. Комментарии объясняют причину решения или ограничение, а не пересказывают строку кода
- Ошибки возвращаются явно и сохраняют причину. Контекст отмены и таймаут передаются через `context.Context`
- Деньги хранятся в целых копейках. Цена одного монитора - `2400`, вычисления через `float64` не используются
- Транзакции короткие. HTTP-запросы к проверяемым сайтам и провайдерам выполняются после освобождения блокировок БД
- `gofmt`, статический анализ и тесты значимых сценариев выполняются при разработке. В первую очередь проверяются границы доступа, конкурентные операции, повторы и восстановление после ошибок

### Авторизация и пример aeroCRM

Модуль `auth` реализован на Go. Формы Next.js обращаются к Go API через proxy того же origin. Авторизация проверяет роль и состояние аккаунта; доступ к мониторам ограничен владельцем и действующей квотой.

Из aeroCRM берем сценарии регистрации по email с подтверждением, входа по паролю, редактирования профиля, смены пароля, просмотра и отзыва сессий. Для админки нужны пользователи, подписки и платежи, мониторы и инциденты, состояние доставок и журнал действий.

Проверенные исходники aeroCRM: локальный checkout `sales-productivity-release`, commit `ef37faa9785b67b4e91effeaea01af4971015ca3`. Основные ориентиры - `identity/src/auth/auth.service.ts`, `CabinetPageClient.tsx` и `admin-navigation.data.ts`. Это проверка исходников, а не новая проверка production.

Для браузера реализованы серверные сессии в PostgreSQL и непрозрачный случайный идентификатор в `HttpOnly` cookie. В режиме HTTPS cookie имеет `Secure`, изменяющие операции защищены от CSRF. В БД хранится хеш идентификатора сессии. Каждый вход создает новую сессию, выход и отзыв делают ее недействительной. Изменение привилегий пока не реализовано и должно отзывать сессии при добавлении административного управления.

Пароли хешируются через `golang.org/x/crypto/argon2`. Подтверждения email и восстановления одноразовые, ограничены сроком и числом попыток. Восстановление дает установить новый пароль после проверки владения email. Сценарий отправки временного пароля из aeroCRM не переносится. Административный доступ закрыт до реализации MFA.

SMS, внешние OAuth-провайдеры и правило одной активной сессии из aeroCRM не включаются автоматически. Их реализация требует отдельной продуктовой потребности. Публичная регистрация не позволяет назначить себе административную роль.

Cloudflare Turnstile защищает формы регистрации, входа и запроса восстановления. Go вызывает Siteverify и проверяет результат, ожидаемые hostname и action. Капча дополняет ограничения попыток, а не заменяет их. Истекший или повторно использованный токен не принимается. Для локальной разработки используются официальные тестовые ключи в отдельной конфигурации. [Проверка на сервере](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [локальное тестирование](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)

#### Локальный контракт auth/accounts

Все маршруты начинаются с `/api/v1`. Для JSON-запросов нужен `Content-Type: application/json`. Неизвестные поля, включая попытку передать роль при регистрации, отклоняются. Изменяющие запросы требуют точного `Origin`, указанного в `AUTH_ORIGIN`; после входа дополнительно нужен `X-CSRF-Token`. HTTP-клиент сохраняет cookie из ответа на вход.

| Метод и маршрут | JSON / результат |
| --- | --- |
| `POST /auth/register` | `{email, name, password, turnstileToken}`; `202`, письмо в Mailpit |
| `POST /auth/verify` | `{token, password}`; подтверждение email, `204` |
| `POST /auth/login` | `{email, password, turnstileToken}`; cookie, `{csrfToken, account}` |
| `GET /auth/csrf` | `{csrfToken}` для действующей cookie-сессии |
| `GET /me` | Текущий профиль |
| `PATCH /me` | `{name}`; обновленный профиль |
| `GET /me/sessions` | Последние 100 активных сессий текущего аккаунта |
| `DELETE /me/sessions/{id}` | Отзыв своей сессии, `204` |
| `DELETE /me/sessions` | Отзыв всех своих сессий и ранее выданных reset-токенов, `204` |
| `POST /auth/logout` | Выход и удаление cookie, `204` |
| `POST /auth/password/change` | `{currentPassword, newPassword}`; смена пароля и отзыв сессий, `204` |
| `POST /auth/password/reset/request` | `{email, turnstileToken}`; одинаковый `202` для существующего и неизвестного email |
| `POST /auth/password/reset/confirm` | `{token, password}`; новый пароль и отзыв всех сессий, `204` |

Регистрация сначала сохраняет заявку, а не действующий аккаунт. Подтверждение требует и токен из письма, и пароль этой заявки: ссылка на чужую предварительную регистрацию не активирует известный злоумышленнику пароль. После подтверждения выполняется обычный вход. Повторная регистрация отправляет новую заявку; уже созданный аккаунт она не изменяет. Пароли не отправляются по email.

Пароль хранится как Argon2id с отдельной случайной солью: 19 MiB памяти, две итерации, один поток. [Рекомендации OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Cookie содержит случайный токен, БД — его SHA-256, отдельный публичный ID сессии и версию учетных данных. Вход и изменение пароля сериализуются по учетной записи. Сброс/смена пароля отзывает ранее открытые сессии; повторное применение токена не допускается.

По умолчанию сессия действует 30 дней, подтверждение email и сброс пароля — 30 минут. Cookie имеет `HttpOnly`, `SameSite=Lax`, `Path=/`; для HTTPS — `Secure` и имя с префиксом `__Host-`. HTTP с незащищенной cookie разрешен только локально. Смена пароля и повторный вход требуют получения нового CSRF-токена. API не доверяет `X-Forwarded-For`: ограничения попыток используют адрес непосредственного соединения и отдельно email. Конфигурация доверенного proxy будет нужна при подготовке деплоя.

Имя: 2–100 символов после удаления крайних пробелов; пароль: 12–1024 байта, без обрезки и скрытого изменения. Параллельно выполняются не более двух вычислений Argon2id; при насыщении API возвращает `503`. Регистрация и запрос восстановления ограничены пятью запросами на email и двадцатью на IP в час. Вход — десять попыток на email и сто на IP за 15 минут; подтверждение и завершение сброса — двадцать на IP за 15 минут. Для одной заявки подтверждения допустимо пять неверных паролей. Смена пароля — десять попыток на аккаунт и двадцать на IP за 15 минут. Превышение лимита дает `429`; неверная сессия — `401`; отказ Origin/CSRF/капчи — `403`. Тело ошибки: `{ "error": "код" }`, без данных БД и провайдера.

`make check` не требует БД и внешних провайдеров. Интеграционные тесты включаются через `HEARTBEAT_TEST_DATABASE_URL`; защита в тестах допускает только проектную PostgreSQL на `127.0.0.1:55432`. Каждый тест создает отдельную БД и удаляет ее после завершения. Live smoke дополнительно включается через `HEARTBEAT_LIVE_AUTH=true`, отправляет письма на уникальный адрес `example.test` в Mailpit и удаляет только собственные сообщения. Пароли, cookie и токены из писем не выводятся в успешном отчете теста.

Для ручной проверки API локальная регистрация (Origin сайта соответствует `AUTH_ORIGIN`):

```sh
curl -i http://127.0.0.1:8080/api/v1/auth/register \
  -H 'Origin: http://127.0.0.1:3000' \
  -H 'Content-Type: application/json' \
  --data '{"email":"demo@example.test","name":"Demo","password":"local-demo-password-2026","turnstileToken":"XXXX.DUMMY.TOKEN.XXXX"}'
```

Письмо доступно в Mailpit: `http://127.0.0.1:58025`. Ссылки из писем ведут на работающие формы Next.js `/verify-email` и `/reset-password`; доступны также `/register`, `/login` и `/forgot-password`. При ручном обращении к API токен из письма передается в JSON `/auth/verify` вместе с паролем.

`TURNSTILE_LOCAL_TEST_MODE=true` допускает только официальные тестовые ключи и `XXXX.DUMMY.TOKEN.XXXX`, но каждый раз вызывает Cloudflare. Живой тестовый ответ проверяется по `metadata.result_with_testing_key`; hostname/action в этом режиме не отражают реальную форму. В обычном режиме требуются точные hostname и action. Локальный тестовый режим допускается только при loopback-адресах API и сайта; внешняя сеть нужна даже для локального smoke. Тестовые ключи не доказывают работу настоящего браузерного challenge: проверка с реальным виджетом и собственными ключами остается частью подготовки публичного запуска.

Для будущего публичного сайта ожидается `TURNSTILE_HOSTNAME=heartbeat-checker.ru`, `AUTH_ORIGIN=https://heartbeat-checker.ru`, secure cookie и выключенный локальный тестовый режим. В виджете Turnstile задается action `register`, `login` или `reset`; Go API получает `turnstileToken` и проверяет action в ответе Siteverify. Собственные ключи в текущем этапе не созданы. На момент проверки панели Cloudflare 18.10.2026 домен ожидал подтверждения nameserver; DNS и настройки зоны в этом этапе не менялись.

SMTP ограничен loopback-приемником. Письма отправляются после транзакции, надежной очереди повторов пока нет. Worker уже очищает истекшие и использованные auth-данные. До внешнего запуска нужны реальный email-провайдер, очередь доставки и MFA для административного доступа. Оставшиеся ограничения записаны в корневом `../backlog.md`; регистрация не выдает административных прав.

### Проверки и инциденты

Рабочее определение монитора: один настроенный HTTP-запрос к одному URL с методом и условиями успешного ответа. Сейчас доступны GET/HEAD, ожидаемый код и поиск текста в теле GET; пользовательские заголовки остаются целевым расширением. Несколько условий для одного ответа не образуют дополнительные платные мониторы. По целевому тарифу повторные проверки и уведомления входят в стоимость.

Для HEAD проверка тела не применяется. Поддержка POST и сложных условий JSON добавляется отдельным сценарием, если нужна. Это техническое ограничение первой реализации, а не дополнительный тариф.

Действующий API под `/api/v1` предоставляет `GET/POST /monitors`, `GET/PATCH/DELETE /monitors/{id}`, `GET /monitors/{id}/results`, `GET /monitors/{id}/incidents` и `GET /entitlement`. Изменения требуют сессии, точного Origin и CSRF-токена. История результатов и инцидентов видна только владельцу монитора. Ответ инцидента содержит `closeReason`: `recovered` после успешной проверки, `config_changed` при изменении настройки, `paused` при остановке и `deleted` при удалении. Это различает восстановление сайта и прекращение наблюдения.

Настройки `intervalMinutes` и `failureThreshold` — целые числа от 1 до 10. POST без этих полей создает монитор с интервалом 5 минут и порогом 2; явные значения вне диапазона отклоняются с `400`. PATCH без полей сохраняет текущие настройки и по-прежнему требует `version`. GET и список всегда возвращают оба значения. Формы создания и редактирования позволяют выбрать их отдельно для каждого монитора.

Миграция `0004_monitor_scheduling.sql` сохраняет существующим мониторам интервал 1 минуту и порог 2; новые получают значения 5 и 2. Ранее примененные миграции не меняются. Изменение интервала или порога использует тот же атомарный путь, что смена URL/условий: новая версия, отмена текущей аренды, сброс серии ошибок и свежего состояния, закрытие открытого инцидента с `config_changed`, ближайшая проверка сразу после сохранения. Повторное сохранение тех же значений и переименование состояние не сбрасывают.

Настройки покрыты PostgreSQL-тестами с `-race`: обновление старой схемы, defaults и валидация API, расписание и свежесть для 1/5/10 минут, пороги 1/3/10, повторы результатов, UNKNOWN и изменение конфигурации с активной арендой. В Chrome проверены создание 5/2, редактирование 10/3 и 1/1, сохранение после reload, обе темы и мобильные формы 320/390 px. Реальные worker/probe получили HTTP200 и назначили следующую проверку через выбранные 5 и 10 минут. Это не нагрузочная приемка количества мониторов.

1. `worker` выбирает наступившие задания через `FOR UPDATE SKIP LOCKED` в короткой транзакции
2. Задание получает `run_id`, версию настроек `config_version`, срок аренды исполнения и токен текущей попытки
3. Транзакция завершается. `worker` вызывает `probe` по закрытому HTTP-интерфейсу с внутренней аутентификацией и ограничением времени
4. `probe` проверяет адрес, выполняет запрос и возвращает ограниченный результат
5. `monitors` принимает результат только для актуальной попытки и конфигурации. Результат и событие `CheckCompleted` записываются одной транзакцией
6. `incidents` последовательно обрабатывает результаты одного монитора. Изменение инцидента и событие для будущей доставки записываются одной транзакцией
7. На следующем этапе `notifications` будет создавать отдельные доставки по каналам. Отправка провайдеру должна происходить вне транзакции

Инцидент открывается при достижении выбранного `failureThreshold` последовательных DOWN: при пороге 1 — после первой ошибки, при 2 — после второй и так далее. Первая успешная проверка закрывает его с причиной `recovered`; доставку уведомлений предстоит реализовать. UNKNOWN обнуляет серию ошибок, не закрывая уже открытый инцидент как восстановленный. Повторы обработки одного результата не считаются новыми проверками. Первый успешный запуск без предшествующего сбоя не создает событие о восстановлении.

Следующая проверка планируется от завершения текущей через `intervalMinutes`; такой же интервал используется при отложенной проверке без доступа. Отсутствие результата или его возраст более двух выбранных интервалов плюс 30 секунд дает состояние `UNKNOWN`: 150 секунд для 1 минуты, 630 для 5 и 1230 для 10. Это проверка свежести отображаемого состояния, она сама по себе не создает инцидент. Ошибка собственного worker или probe не доказывает падение сайта. Пауза и окончание подписки имеют отдельный статус, а не имитируют инцидент на стороне пользователя.

Аренда задания и токен попытки позволяют восстановиться после падения worker и отклонить запоздалый результат. Обработка событий сохраняет порядок внутри монитора, а повторное событие не меняет состояние второй раз. После простоя не выполняется залп всех пропущенных проверок. Параллелизм ограничен по системе, аккаунту и целевому адресу.

Выбранный интервал не является обещанием срока доставки уведомления. В задержку входят ожидание очередной проверки, таймаут, число сбоев для подтверждения и доставка. Перед коммерческим запуском отдельно проверяется влияние места размещения probe на ложные срабатывания.

### Изоляция probe

`probe` не подключается к PostgreSQL и не получает ключи ЮKassa, SMTP или ботов. Он принимает только данные конкретной проверки от worker по внутреннему интерфейсу с общим секретом и возвращает ограниченный результат. Локально интерфейс слушает loopback; публиковать его для пользователей нельзя.

Исполнитель защищается от SSRF: разрешенные схемы и порты, запрет внутренних и служебных IPv4/IPv6, проверка каждого DNS-результата и редиректа, соединение только с проверенным адресом. Повторное разрешение имени не должно позволять обойти проверку через DNS rebinding. Сетевые ограничения окружения дополняют проверки в коде.

Текущие ограничения: только публичные GET/HEAD по `http:80` и `https:443`, до 10 секунд на проверку, до 1 MiB тела ответа, до трех перенаправлений и до четырех проверенных DNS-адресов для fallback. Одновременно выполняются не более четырех проверок в целом, двух на аккаунт и одной на целевой адрес. Каждый DNS-результат и новый адрес перенаправления проходят повторную проверку; полное тело ответа в историю не сохраняется. Пользовательские заголовки и учетные данные проверяемого API пока не принимаются.

### Платежи и подписка

Сейчас `billing` хранит только действующее право на квоту мониторов и предоставляет локальную команду явной выдачи тестового права. При регистрации квота равна нулю; `local_test` недействителен в production. Заказы, платежи, возвраты и автопродление ниже описывают целевую архитектуру, а не работающую интеграцию. В ней ЮKassa проводит платежные операции, а правила подписки и расписание списаний принадлежат Heartbeat Checker.

1. Go рассчитывает сумму по серверному тарифу и сохраняет заказ с квотой и периодом
2. До запроса в ЮKassa сохраняются попытка платежа и ключ идемпотентности
3. Пользователь оплачивает заказ на платежной странице ЮKassa
4. После webhook или фоновой сверки Go запрашивает платеж у ЮKassa и проверяет успешный статус, сумму, валюту, магазин и связь с локальным заказом
5. Подтвержденная оплата атомарно изменяет квоту и оплаченный срок. Повторное уведомление не выдает доступ повторно

Возврат браузера с платежной страницы не подтверждает оплату. При сетевой ошибке результат сначала сверяется с провайдером. Повтор одной операции использует исходный ключ. ЮKassa поддерживает его идемпотентность 24 часа, поэтому неизвестное списание после этого срока не повторяется автоматически. [Формат API](https://yookassa.ru/developers/using-api/interaction-format), [webhooks](https://yookassa.ru/developers/using-api/webhooks)

Добровольное автопродление требует сохраненного согласия пользователя и подтвержденного сохранения способа оплаты. У платежа продления есть уникальная связь с подпиской и расчетным периодом. Отключение автопродления проверяется перед новым списанием. Подключение автоплатежей к реальному магазину проверяется перед запуском. [Автоплатежи ЮKassa](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/recurring-payments/basics)

При докупке квоты расчет и правило округления фиксируются в заказе. При уменьшении квоты пользователь заранее выбирает мониторы, которые останутся включенными. С начала следующего периода планировщик применяет новый лимит и приостанавливает остальные, сохраняя историю. Создание и включение мониторов проверяют квоту конкурентно, чтобы два одновременных запроса не превысили лимит. Пауза отдельного монитора не отменяет оплаченную квоту.

После окончания оплаты worker прекращает новые проверки. Поздний результат не снимает ограничение подписки. Доступ к кабинету, оплате и истории в пределах срока хранения сохраняется. Правила возвратов и параметры чеков оформляются до реальных платежей с учетом настроек продавца.

### Доставка уведомлений

Привязки получателей создаются через сайт с подтверждением владения каналом. Бот Telegram нужен для технической доставки и привязки, отдельное управление сервисом в боте не разрабатывается.

Для Telegram клиент выбирает получателя: личный чат с ботом, группу/супергруппу или конкретный топик группы с включенными темами. Получатели привязываются в кабинете и затем выбираются в настройках монитора. Для группы без выбранного топика отправка идет в общий чат; для выбранного топика сохраняется отдельный `message_thread_id` вместе с `chat_id`. Разные топики одной группы являются разными получателями. Это требование пользователя от 18.10.2026 к будущему модулю доставки, а не уже работающая отправка.

Привязка выполняется одноразовым ограниченным по времени кодом из кабинета и подтверждается действием пользователя в нужном чате/топике. Для группы проверяются права связывающего пользователя и право бота отправлять сообщения; одного введенного ID недостаточно. В кабинете отображаются название чата, выбранный топик и состояние связи. Удаление бота, запрет отправки, удаленный или закрытый топик дают видимую ошибку доставки; автоматического переноса сообщения из выбранного топика в общий чат нет. Миграция группы в супергруппу должна сохранять связь с учетом нового `chat_id`. При удалении получателя прекращаются новые доставки этому адресу. [Telegram: sendMessage](https://core.telegram.org/bots/api#sendmessage), [привязка через deep link](https://core.telegram.org/bots/features#deep-linking)

Каждая доставка хранит канал, получателя, событие, статус и попытки. Для Telegram, email и MAX используются отдельные адаптеры и ограничения скорости. Повторы учитывают ответы провайдера, включая `retry_after`, имеют ограничение попыток и видимую причину окончательной ошибки.

События сбоя и восстановления обрабатываются последовательно для конкретного монитора и получателя. Ошибка одного канала не останавливает остальные. Успешный ответ API провайдера означает прием сообщения провайдером, а не прочтение пользователем. При потере ответа после успешной отправки возможен дубль, гарантии `exactly once` нет.

### Локальная разработка и порядок реализации

Локальное окружение уже включает Go API, worker, probe, Next.js, PostgreSQL и Mailpit; команды запуска приведены выше. Платежи и каналы уведомлений пока не реализованы, поэтому сквозной платежный или уведомительный сценарий не заявлен. Сетевой тест Turnstile использует официальные тестовые ключи и требует доступа к Cloudflare. Это не полностью автономный режим без интернета.

Тестовые упрощения включаются только явной локальной конфигурацией. Они не дают скрытого обхода авторизации, оплаченных лимитов или защиты URL. Секреты находятся в локальных игнорируемых файлах. Пример конфигурации содержит только названия параметров и безопасные значения.

Реализованы каркас Go, конфигурация, PostgreSQL и миграции, auth с Turnstile, сессиями и профилем, локальная квота и ее проверка, мониторы, планировщик, probe, результаты, инциденты, очистка истории и истекших auth-данных, лендинг и основной кабинет. Подробные результаты сохраняются 7 дней; закрытые инциденты, дневная статистика и обработанные события outbox — 90 дней. Worker удаляет просроченные данные ограниченными порциями. Дальнейшие этапы: оплаченная подписка и ЮKassa, доставки Telegram/email/MAX, административный интерфейс, сквозная проверка браузера и отдельная подготовка деплоя.

При проверке ключевыми являются изоляция аккаунтов, SSRF, истечение сессий, повторные webhooks, конкурентное изменение квоты, перезапуск worker и ошибки внешних провайдеров. Готовность к реальному запуску требует отдельной проверки магазина ЮKassa, почты, ботов, резервного копирования и восстановления.
