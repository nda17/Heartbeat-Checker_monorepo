# Heartbeat-Checker_monorepo

## Архитектура:

Heartbeat Checker - коммерческий сервис проверки доступности сайтов и API. Пользователь управляет мониторингом через сайт и получает уведомления о падении и восстановлении.

Домен проекта — `heartbeat-checker.ru`, будущий публичный origin — `https://heartbeat-checker.ru`. Сейчас приложение запускается только локально; домен не меняет локальные адреса и тестовые ключи.

Документ описывает целевую архитектуру и локальную реализацию. Решения и исходники актуализированы 18.10.2026. Мониторы, платежи и frontend пока описывают предстоящую реализацию; ниже отдельно указан статус Go API авторизации.

### Текущее состояние и запуск

Реализован Go API: конфигурация с валидацией, подключение PostgreSQL, структурированные логи и корректное завершение. `/healthz` проверяет работу HTTP-сервера, `/readyz` выполняет реальный Ping БД с таймаутом. При недоступной БД readiness возвращает 503, а после восстановления снова 200.

Требуются Go 1.27+, Docker с Compose и `make`. PostgreSQL 18.6 запускается на `127.0.0.1:55432` в отдельном Compose-проекте. Образ закреплен по digest. Данные сохраняются в volume этого проекта.

Из корня монорепозитория:

```sh
make local-up # Запустить PostgreSQL и локальный SMTP-приемник Mailpit
make migrate  # Применить SQL-миграции auth/accounts отдельной командой
make run    # Запустить API на 127.0.0.1:8080, остановка через Ctrl+C
```

В другом терминале:

```sh
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
make check  # Форматирование, go vet, тесты и сборка
make test-integration # HTTP/SQL-сценарии в отдельных временных БД
make test-smtp-auth   # Реальные PostgreSQL и Mailpit, заглушка капчи
make test-live-auth   # Реальные Siteverify и SMTP Mailpit, нужна внешняя сеть
```

`make db-up` запускает только PostgreSQL, `make mail-up` — только Mailpit. `make db-down` останавливает контейнеры локального Compose-проекта, сохраняя volume БД. Почта Mailpit временная и не сохраняется после удаления контейнера. Тестовые учетные данные предназначены только для локального окружения.

`make run` задает локальные значения `DATABASE_URL`, `AUTH_ORIGIN`, cookie, Turnstile и SMTP; экспортированные переменные их переопределяют. При прямом запуске Go обязательны `DATABASE_URL` и полный набор параметров auth из `.env.example`. Неполная конфигурация останавливает запуск. API не применяет миграции автоматически. `make migrate` требует только настройки БД, блокирует конкурентное применение, записывает контрольные суммы и отклоняет изменение уже примененного SQL.

`.env.example` описывает параметры и не загружается автоматически. Приложение читает environment. Таймауты по умолчанию: соединение с БД 5 секунд, readiness 2 секунды, завершение 10 секунд. PostgreSQL запущен для локальной работы, процесс API после проверки остановлен.

Foundation проверен через `make check`, доступность HTTP с реальной БД, отказ readiness при остановке БД, восстановление readiness и завершение по SIGTERM. Frontend, worker, probe, платежи и каналы уведомлений мониторинга еще не реализованы. Деплой не выполнялся.

Для auth/accounts 18.10.2026 прошли `make check`, `go mod verify`, весь набор тестов с `-race` и реальной PostgreSQL, повторное применение миграций, SMTP smoke и `make test-live-auth`. Живой сценарий проверил Siteverify с официальными тестовыми ключами, регистрацию, письмо, подтверждение, вход, сброс пароля, отзыв старой сессии и повторный вход. Временные БД и письма тестов удалены. Это проверка Go API и адаптеров; браузерные формы еще не реализованы.

На этой машине LuLu задерживал первое внешнее соединение каждого нового временного Go-бинарника. После временного отключения LuLu пользователем полный live smoke прошел. При повторении таймаута нужно проверить разрешение конкретного Go-процесса в локальном сетевом фильтре; таймаут Siteverify и проверка TLS в коде не ослаблялись.

### Принятые решения

- Весь backend, включая регистрацию, вход, сессии, платежи и проверку прав, пишется на Go
- Frontend - Next.js с архитектурой Feature-Sliced Design (FSD). Лендинг, личный кабинет и административный интерфейс используют общие компоненты
- Пользовательские сценарии входа, кабинета и управления пользователями берем за образец из aeroCRM и адаптируем под мониторинг
- Better Auth и Keycloak в стартовую архитектуру не входят
- Капча - Cloudflare Turnstile. Токен проверяет Go-backend
- Настройки и управление находятся на сайте. Telegram и MAX используются для уведомлений и привязки получателя
- Каналы уведомлений - Telegram, email и MAX
- Цена - 24 ₽ за монитор в месяц. Пользователь оплачивает квоту из N мониторов и может заменять URL внутри нее
- Оплата через ЮKassa. Доступны ручное продление и добровольное автопродление
- Пробного периода нет. Проверки запускаются в пределах оплаченной квоты
- Докупка квоты оплачивается пропорционально остатку периода. Уменьшение применяется со следующего периода
- Отмена автопродления сохраняет доступ до конца оплаченного срока. После окончания оплаты проверки приостанавливаются, кабинет и сохраненная история остаются доступны
- Каждый адрес проверяется раз в минуту. Две неудачные проверки подряд открывают инцидент, первая успешная закрывает его
- Подробные результаты хранятся 7 дней. Инциденты и сводная статистика - 90 дней
- Сейчас разработка и проверка выполняются локально. Деплой будет отдельным этапом

### Основной подход

Модульный монолит на Go: одна кодовая база и один `go.mod`, разделенные на бизнес-модули с явными границами. Модули вызывают публичные контракты друг друга или обмениваются сохраняемыми событиями. HTTP между бизнес-модулями внутри процесса не нужен.

Из одной кодовой базы собираются три процесса. `api` обслуживает сайт, `worker` выполняет фоновую работу, `probe` обращается к проверяемым URL. Такое разделение позволяет ограничить доступ исполнителя HTTP-проверок и отдельно управлять его нагрузкой.

| Компонент | Ответственность |
| --- | --- |
| Next.js | Страницы, формы, отображение данных и серверный рендеринг интерфейса |
| Reverse proxy | Единый origin для сайта и API. В дальнейшем HTTPS и внешняя маршрутизация |
| `api` | HTTP API, аутентификация, права, пользовательские операции, webhooks провайдеров |
| `worker` | Планирование проверок, обработка результатов и событий, доставки, продления и очистка истории |
| `probe` | Ограниченное выполнение запросов к пользовательским адресам |
| PostgreSQL | Данные приложения, сессии, задания, результаты, события и учет доставок |

Для старта используется PostgreSQL без Redis и отдельного брокера сообщений. Сохраняемые задания и transactional outbox обеспечивают восстановление фоновой работы после перезапуска. Outbox - запись события в той же транзакции, что и изменение бизнес-данных.

Отдельный API Gateway не нужен. Маршрутизация остается в reverse proxy, а проверка сессий и прав - в Go. Выделение новых сервисов или брокера рассматривается при измеримой потребности в независимом масштабировании, изоляции или пропускной способности.

### Frontend по FSD

Маршруты Next.js находятся в `apps/web/app`, а FSD-код - в `apps/web/src`. Слои App и Pages называются `_app` и `_pages`, чтобы не конфликтовать с особыми каталогами Next.js. Файл маршрута подключает готовую страницу, сам интерфейс находится в соответствующем слайсе. [FSD и Next.js](https://feature-sliced.design/docs/guides/tech/with-nextjs)

Порядок зависимостей: `_app > _pages > widgets > features > entities > shared`. Код импортирует нижние слои. Слайсы одного слоя изолированы, например `features/create-monitor` не импортирует `features/delete-monitor`. Их взаимодействие собирается на уровне страницы или виджета. [Слои FSD](https://feature-sliced.design/docs/reference/layers)

- Слайс называется по своему назначению. Например, `features/create-monitor` или `entities/incident`
- Внутри слайса используются нужные сегменты: `ui`, `model`, `api`, `lib`. Пустые сегменты не создаются
- Между слайсами используются явные публичные экспорты `index.ts`. Импорт внутренних файлов чужого слайса не допускается
- `shared/ui` не знает о мониторах и подписках. `shared/api` содержит общий транспорт, а запросы конкретной сущности находятся в ее слайсе
- Server-only код имеет отдельный публичный вход, если слайс используется и серверными, и клиентскими компонентами. Он не попадает в клиентский bundle
- Next.js отвечает за интерфейс и его рендеринг. Авторизация, платежные решения, права и бизнес-правила выполняются Go API
- Границы слоев и слайсов проверяются линтером при создании frontend. Сейчас frontend еще не реализован

### Правила модулей и читаемости кода

- `domain` не импортирует SQL, HTTP, провайдеров или соседние модули
- `service` описывает сценарий. Интерфейс зависимости определяется там, где он нужен, без интерфейса на каждый тип
- HTTP-обработчик проверяет формат запроса, вызывает сценарий и формирует ответ. SQL и бизнес-правила в обработчик не помещаются
- Репозиторий отвечает за хранение. Решения о тарифе, доступности сайта и правах остаются в прикладных сценариях и домене
- Каждый модуль владеет своими таблицами. Чтение и изменение чужих таблиц через собственный SQL не допускаются
- Для вызовов другого модуля используются `contracts`. Закрытые доменные типы и репозитории наружу не выдаются
- `module.go` собирает реализацию и предоставляет контракты и HTTP-обработчики. Только `app` связывает модули между собой
- Вложенный `internal` запрещает импорт реализации соседним модулем и пакетом `app`. `app` получает доступ через `module.go`
- `contracts` не зависит от собственного закрытого `internal`. Циклических импортов и обратной зависимости `platform` от модулей нет
- Зависимости передаются обычными конструкторами. Глобальные сервисы, скрытый service locator и DI-фреймворк не нужны
- `platform` содержит технические механизмы без бизнес-правил. Общий `pkg` и универсальные `helpers` заранее не создаются
- Функции имеют понятные имена и одну задачу. Комментарии объясняют причину решения или ограничение, а не пересказывают строку кода
- Ошибки возвращаются явно и сохраняют причину. Контекст отмены и таймаут передаются через `context.Context`
- Деньги хранятся в целых копейках. Цена одного монитора - `2400`, вычисления через `float64` не используются
- Транзакции короткие. HTTP-запросы к проверяемым сайтам и провайдерам выполняются после освобождения блокировок БД
- `gofmt`, статический анализ и тесты значимых сценариев выполняются при разработке. В первую очередь проверяются границы доступа, конкурентные операции, повторы и восстановление после ошибок

### Авторизация и пример aeroCRM

Модуль `auth` реализован на Go. Будущие формы Next.js обращаются к Go API. Авторизация проверяет роль и состояние аккаунта; доступ к конкретным мониторам будет проверяться при реализации модуля мониторинга.

Из aeroCRM берем сценарии регистрации по email с подтверждением, входа по паролю, редактирования профиля, смены пароля, просмотра и отзыва сессий. Для админки нужны пользователи, подписки и платежи, мониторы и инциденты, состояние доставок и журнал действий.

Проверенные исходники aeroCRM: локальный checkout `sales-productivity-release`, commit `ef37faa9785b67b4e91effeaea01af4971015ca3`. Основные ориентиры - `identity/src/auth/auth.service.ts`, `CabinetPageClient.tsx` и `admin-navigation.data.ts`. Это проверка исходников, а не новая проверка production.

Для браузера реализованы серверные сессии в PostgreSQL и непрозрачный случайный идентификатор в `HttpOnly` cookie. В режиме HTTPS cookie имеет `Secure`, изменяющие операции защищены от CSRF. В БД хранится хеш идентификатора сессии. Каждый вход создает новую сессию, выход и отзыв делают ее недействительной. Изменение привилегий пока не реализовано и должно отзывать сессии при добавлении административного управления.

Пароли хешируются через `golang.org/x/crypto/argon2`. Подтверждения email и восстановления одноразовые, ограничены сроком и числом попыток. Восстановление дает установить новый пароль после проверки владения email. Сценарий отправки временного пароля из aeroCRM не переносится. Административный доступ закрыт до реализации MFA.

SMS, внешние OAuth-провайдеры и правило одной активной сессии из aeroCRM не включаются автоматически. Их реализация требует отдельной продуктовой потребности. Публичная регистрация не позволяет назначить себе административную роль.

Cloudflare Turnstile защищает формы регистрации, входа и запроса восстановления. Go вызывает Siteverify и проверяет результат, ожидаемые hostname и action. Капча дополняет ограничения попыток, а не заменяет их. Истекший или повторно использованный токен не принимается. Для локальной разработки используются официальные тестовые ключи в отдельной конфигурации. [Проверка на сервере](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [локальное тестирование](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)

#### Локальный контракт auth/accounts

Все маршруты начинаются с `/api/v1`. Для JSON-запросов нужен `Content-Type: application/json`. Неизвестные поля, включая попытку передать роль при регистрации, отклоняются. Изменяющие запросы требуют точного `Origin`, указанного в `AUTH_ORIGIN`; после входа дополнительно нужен `X-CSRF-Token`. HTTP-клиент сохраняет cookie из ответа на вход.

| Метод и маршрут | JSON / результат |
| --- | --- |
| `POST /auth/register` | `{email, name, password, turnstileToken}`; `202`, письмо в Mailpit |
| `POST /auth/verify` | `{token, password}`; подтверждение email, `204` |
| `POST /auth/login` | `{email, password, turnstileToken}`; cookie, `{csrfToken, account}` |
| `GET /auth/csrf` | `{csrfToken}` для действующей cookie-сессии |
| `GET /me` | Текущий профиль |
| `PATCH /me` | `{name}`; обновленный профиль |
| `GET /me/sessions` | Последние 100 активных сессий текущего аккаунта |
| `DELETE /me/sessions/{id}` | Отзыв своей сессии, `204` |
| `DELETE /me/sessions` | Отзыв всех своих сессий и ранее выданных reset-токенов, `204` |
| `POST /auth/logout` | Выход и удаление cookie, `204` |
| `POST /auth/password/change` | `{currentPassword, newPassword}`; смена пароля и отзыв сессий, `204` |
| `POST /auth/password/reset/request` | `{email, turnstileToken}`; одинаковый `202` для существующего и неизвестного email |
| `POST /auth/password/reset/confirm` | `{token, password}`; новый пароль и отзыв всех сессий, `204` |

Регистрация сначала сохраняет заявку, а не действующий аккаунт. Подтверждение требует и токен из письма, и пароль этой заявки: ссылка на чужую предварительную регистрацию не активирует известный злоумышленнику пароль. После подтверждения выполняется обычный вход. Повторная регистрация отправляет новую заявку; уже созданный аккаунт она не изменяет. Пароли не отправляются по email.

Пароль хранится как Argon2id с отдельной случайной солью: 19 MiB памяти, две итерации, один поток. [Рекомендации OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Cookie содержит случайный токен, БД — его SHA-256, отдельный публичный ID сессии и версию учетных данных. Вход и изменение пароля сериализуются по учетной записи. Сброс/смена пароля отзывает ранее открытые сессии; повторное применение токена не допускается.

По умолчанию сессия действует 30 дней, подтверждение email и сброс пароля — 30 минут. Cookie имеет `HttpOnly`, `SameSite=Lax`, `Path=/`; для HTTPS — `Secure` и имя с префиксом `__Host-`. HTTP с незащищенной cookie разрешен только локально. Смена пароля и повторный вход требуют получения нового CSRF-токена. API не доверяет `X-Forwarded-For`: ограничения попыток используют адрес непосредственного соединения и отдельно email. Конфигурация доверенного proxy будет нужна при подготовке деплоя.

Имя: 2–100 символов после удаления крайних пробелов; пароль: 12–1024 байта, без обрезки и скрытого изменения. Параллельно выполняются не более двух вычислений Argon2id; при насыщении API возвращает `503`. Регистрация и запрос восстановления ограничены пятью запросами на email и двадцатью на IP в час. Вход — десять попыток на email и сто на IP за 15 минут; подтверждение и завершение сброса — двадцать на IP за 15 минут. Для одной заявки подтверждения допустимо пять неверных паролей. Смена пароля — десять попыток на аккаунт и двадцать на IP за 15 минут. Превышение лимита дает `429`; неверная сессия — `401`; отказ Origin/CSRF/капчи — `403`. Тело ошибки: `{ "error": "код" }`, без данных БД и провайдера.

`make check` не требует БД и внешних провайдеров. Интеграционные тесты включаются через `HEARTBEAT_TEST_DATABASE_URL`; защита в тестах допускает только проектную PostgreSQL на `127.0.0.1:55432`. Каждый тест создает отдельную БД и удаляет ее после завершения. Live smoke дополнительно включается через `HEARTBEAT_LIVE_AUTH=true`, отправляет письма на уникальный адрес `example.test` в Mailpit и удаляет только собственные сообщения. Пароли, cookie и токены из писем не выводятся в успешном отчете теста.

Для ручной проверки локальная регистрация:

```sh
curl -i http://127.0.0.1:8080/api/v1/auth/register \
  -H 'Origin: http://127.0.0.1:8080' \
  -H 'Content-Type: application/json' \
  --data '{"email":"demo@example.test","name":"Demo","password":"local-demo-password-2026","turnstileToken":"XXXX.DUMMY.TOKEN.XXXX"}'
```

Письмо доступно в Mailpit: `http://127.0.0.1:58025`. Формы Next.js еще нет: токен из письма передается в JSON `/auth/verify` вместе с паролем. Ссылки из писем предназначены для будущих frontend-страниц.

`TURNSTILE_LOCAL_TEST_MODE=true` допускает только официальные тестовые ключи и `XXXX.DUMMY.TOKEN.XXXX`, но каждый раз вызывает Cloudflare. Живой тестовый ответ проверяется по `metadata.result_with_testing_key`; hostname/action в этом режиме не отражают реальную форму. В обычном режиме требуются точные hostname и action. Внешняя сеть нужна даже для локального smoke. Тестовые ключи не доказывают работу настоящего браузерного challenge: проверка с реальным виджетом и собственными ключами остается частью frontend/подготовки запуска.

Для будущего публичного сайта ожидается `TURNSTILE_HOSTNAME=heartbeat-checker.ru`, `AUTH_ORIGIN=https://heartbeat-checker.ru`, secure cookie и выключенный локальный тестовый режим. В виджете Turnstile задается action `register`, `login` или `reset`; Go API получает `turnstileToken` и проверяет action в ответе Siteverify. Собственные ключи в текущем этапе не созданы. На момент проверки панели Cloudflare 18.10.2026 домен ожидал подтверждения nameserver; DNS и настройки зоны в этом этапе не менялись.

SMTP ограничен loopback-приемником. Письма отправляются после транзакции, надежной очереди повторов пока нет. До внешнего запуска нужны реальный email-провайдер, очередь доставки, очистка истекших auth-данных и MFA для административного доступа. Эти ограничения записаны в корневом `../backlog.md`; регистрация не выдает административных прав.

### Проверки и инциденты

Рабочее определение монитора: один настроенный HTTP-запрос к одному URL с методом, заголовками и условиями успешного ответа. Несколько условий для одного ответа не образуют дополнительные платные мониторы. Повторные проверки и уведомления входят в стоимость.

Для начала предлагаются GET/HEAD, проверка кода ответа и наличия текста. Для HEAD проверка тела не применяется. Поддержка POST и сложных условий JSON добавляется отдельным сценарием, если нужна. Это техническое ограничение первой реализации, а не дополнительный тариф.

1. `worker` выбирает наступившие задания через `FOR UPDATE SKIP LOCKED` в короткой транзакции
2. Задание получает `run_id`, версию настроек `config_version`, срок аренды исполнения и токен текущей попытки
3. Транзакция завершается. `worker` вызывает `probe` по закрытому HTTP-интерфейсу с внутренней аутентификацией и ограничением времени
4. `probe` проверяет адрес, выполняет запрос и возвращает ограниченный результат
5. `monitors` принимает результат только для актуальной попытки и конфигурации. Результат и событие `CheckCompleted` записываются одной транзакцией
6. `incidents` последовательно обрабатывает результаты одного монитора. Изменение инцидента и событие для уведомления записываются одной транзакцией
7. `notifications` создает отдельные доставки по каналам. Отправка провайдеру происходит вне транзакции

Две последовательные неудачные проверки открывают один инцидент. Первая успешная проверка закрывает его и создает уведомление о восстановлении. Повторы обработки одного результата не считаются новыми проверками. Первый успешный запуск без предшествующего сбоя не создает уведомление о восстановлении.

При отсутствии свежих результатов состояние считается неизвестным (`UNKNOWN`). Ошибка собственного worker или probe не доказывает падение сайта. Пауза и окончание подписки имеют отдельный статус, а не имитируют инцидент на стороне пользователя.

Аренда задания и токен попытки позволяют восстановиться после падения worker и отклонить запоздалый результат. Обработка событий сохраняет порядок внутри монитора, а повторное событие не меняет состояние второй раз. После простоя не выполняется залп всех пропущенных проверок. Параллелизм ограничен по системе, аккаунту и целевому адресу.

Период проверки в одну минуту не является обещанием доставки уведомления за минуту. В задержку входят ожидание очередной проверки, таймаут, подтверждение сбоя и доставка. Перед коммерческим запуском отдельно проверяется влияние места размещения probe на ложные срабатывания.

### Изоляция probe

`probe` не подключается к PostgreSQL и не получает ключи ЮKassa, SMTP или ботов. Он принимает только данные конкретной проверки и возвращает результат вызывающему worker. Его служебный интерфейс не публикуется для пользователей.

Исполнитель защищается от SSRF: разрешенные схемы и порты, запрет внутренних и служебных IPv4/IPv6, проверка каждого DNS-результата и редиректа, соединение только с проверенным адресом. Повторное разрешение имени не должно позволять обойти проверку через DNS rebinding. Сетевые ограничения окружения дополняют проверки в коде.

Задаются таймауты DNS, соединения, TLS, ожидания ответа и всей операции. Ограничиваются размер ответа, число перенаправлений и параллелизм. Учетные данные проверяемого API передаются только для нужного задания и не попадают в логи. Полные тела ответов по умолчанию не сохраняются в истории.

### Платежи и подписка

`billing` хранит квоту, цену, оплаченный период, локальные заказы, платежи, возвраты и согласие на автопродление. ЮKassa проводит платежные операции. Правила подписки и расписание списаний принадлежат Heartbeat Checker.

1. Go рассчитывает сумму по серверному тарифу и сохраняет заказ с квотой и периодом
2. До запроса в ЮKassa сохраняются попытка платежа и ключ идемпотентности
3. Пользователь оплачивает заказ на платежной странице ЮKassa
4. После webhook или фоновой сверки Go запрашивает платеж у ЮKassa и проверяет успешный статус, сумму, валюту, магазин и связь с локальным заказом
5. Подтвержденная оплата атомарно изменяет квоту и оплаченный срок. Повторное уведомление не выдает доступ повторно

Возврат браузера с платежной страницы не подтверждает оплату. При сетевой ошибке результат сначала сверяется с провайдером. Повтор одной операции использует исходный ключ. ЮKassa поддерживает его идемпотентность 24 часа, поэтому неизвестное списание после этого срока не повторяется автоматически. [Формат API](https://yookassa.ru/developers/using-api/interaction-format), [webhooks](https://yookassa.ru/developers/using-api/webhooks)

Добровольное автопродление требует сохраненного согласия пользователя и подтвержденного сохранения способа оплаты. У платежа продления есть уникальная связь с подпиской и расчетным периодом. Отключение автопродления проверяется перед новым списанием. Подключение автоплатежей к реальному магазину проверяется перед запуском. [Автоплатежи ЮKassa](https://yookassa.ru/developers/payment-acceptance/scenario-extensions/recurring-payments/basics)

При докупке квоты расчет и правило округления фиксируются в заказе. При уменьшении квоты пользователь заранее выбирает мониторы, которые останутся включенными. С начала следующего периода планировщик применяет новый лимит и приостанавливает остальные, сохраняя историю. Создание и включение мониторов проверяют квоту конкурентно, чтобы два одновременных запроса не превысили лимит. Пауза отдельного монитора не отменяет оплаченную квоту.

После окончания оплаты worker прекращает новые проверки. Поздний результат не снимает ограничение подписки. Доступ к кабинету, оплате и истории в пределах срока хранения сохраняется. Правила возвратов и параметры чеков оформляются до реальных платежей с учетом настроек продавца.

### Доставка уведомлений

Привязки получателей создаются через сайт с подтверждением владения каналом. Бот Telegram нужен для технической доставки и привязки, отдельное управление сервисом в боте не разрабатывается.

Каждая доставка хранит канал, получателя, событие, статус и попытки. Для Telegram, email и MAX используются отдельные адаптеры и ограничения скорости. Повторы учитывают ответы провайдера, включая `retry_after`, имеют ограничение попыток и видимую причину окончательной ошибки.

События сбоя и восстановления обрабатываются последовательно для конкретного монитора и получателя. Ошибка одного канала не останавливает остальные. Успешный ответ API провайдера означает прием сообщения провайдером, а не прочтение пользователем. При потере ответа после успешной отправки возможен дубль, гарантии `exactly once` нет.

### Локальная разработка и порядок реализации

Сначала поднимается локальное окружение: Go API, worker, probe, Next.js, PostgreSQL и локальный SMTP-приемник. Платежи и уведомления проверяются через заглушки и тестовые интеграции. Сетевой тест Turnstile использует официальные тестовые ключи и требует доступа к Cloudflare. Это не полностью автономный режим без интернета.

Тестовые упрощения включаются только явной локальной конфигурацией. Они не дают скрытого обхода авторизации, оплаченных лимитов или защиты URL. Секреты находятся в локальных игнорируемых файлах. Пример конфигурации содержит только названия параметров и безопасные значения.

1. Каркас Go, конфигурация, PostgreSQL, миграции, health/readiness и локальный запуск
2. Авторизация и профиль по сценариям aeroCRM, Turnstile, сессии, проверка прав и административного доступа
3. Мониторы, планировщик, изолированный probe, результаты и инциденты
4. Подписка и ЮKassa в тестовом режиме, квоты и ограничения доступа
5. Доставки Telegram, email и MAX, история и интерфейсы кабинета и админки
6. Продающий лендинг, сквозная локальная проверка и подготовка отдельного этапа деплоя

При проверке ключевыми являются изоляция аккаунтов, SSRF, истечение сессий, повторные webhooks, конкурентное изменение квоты, перезапуск worker и ошибки внешних провайдеров. Готовность к реальному запуску требует отдельной проверки магазина ЮKassa, почты, ботов, резервного копирования и восстановления.
